The device path is one appliance per company: everything on one box, reached
by people on the same network. This page is its map.

It still ships, works, and gets bug fixes, but nothing new is designed against
it. To run internkim, use [the host](/docs/running-the-host).

The model sizes below and the Cloud Hypervisor guest come from the Jetson Orin
Nano Super this path was built on. [The host](/docs/running-the-host) is the same
software on any macOS or Linux computer a company already leaves on.

## What runs on the box

```
operator on the same network ── the appliance
                                 ├── buzz-relay (the messenger)
                                 ├── internkim-admind (127.0.0.1:18080)
                                 ├── internkim-capabilityd
                                 ├── llama-server (generation and embedding)
                                 └── Cloud Hypervisor blueclaw guest :8080
```

| Component | Job | Code |
|---|---|---|
| `internkim-admind` | the device admin API: admin UI reverse proxy, backup and restore, OTA apply | `cmd/internkim-admind/`, `internal/admind/` |
| `internkim-capabilityd` | holds the OpenRouter key, the local model and messenger credentials; exposes only a capability API | `internal/capabilityd/` |
| the blueclaw guest | the agent, isolated in a Cloud Hypervisor VM under `blueclaw-supervisor`, reading `/workspace/.blueclaw/config/*.json` | `.dependency/blueclaw/` |
| the local model | a resident `llama-server`: gemma-4-E2B QAT with MTP drafting for generation, BGE-M3 Q8 on CPU for embedding | — |
| the messenger | a Buzz relay on the box, with its media store and its `chatd` adapter | `internal/provisioning/steps/step_buzz_*.go` |

The remote provider is the default path for generation; the local model is
the fallback that keeps the company running when that path is unavailable or
too expensive.

## Where things live on disk

Credentials sit under `/root/.internkim/`, split so each process reads only
its own.

| Path | Read by |
|---|---|
| `/root/.internkim/secrets/openrouter-api-key` | `internkim-capabilityd` |
| `/root/.internkim/models/*` | `internkim-capabilityd`, the model wrapper |

The agent's side is `/root/.blueclaw/`: `config/runtime.json` and
`config/policy.json` are the runtime contract, and `workspace/` is mounted
into the guest as `/workspace`. The workspace's permission model is in
[Boundaries](/docs/boundaries).

## The device browser

The device's Moli browser handles plain public-text navigation. Each requester
gets a Moli of their own with its own profile, so one person's sign-ins never
reach another's; capabilityd starts it on first use and stops it after ten idle
minutes. At most four run at once (`--device-browser-capacity`): the least
recently used is stopped to make room, and while every one is still starting
the agent tells the requester the browser is busy. Login, MFA, captcha,
sensitive inputs and account-risky actions are not done in the device browser;
the agent says what blocks it and stops.

## Setting up a device

From a Mac with an NVIDIA Jetson Orin Nano Super Developer Kit booted on JetPack
(NVMe storage recommended), reachable over SSH, and an
[OpenRouter API key](https://openrouter.ai/keys):

```bash
make build
./internkim setup --board jetson-orin-nano --host <jetson-ip> --user <ssh-user>
```

`./internkim` is a local binary that does not rebuild itself, so run `make build`
again after changing Go, provisioning or runtime configuration. A full setup runs
every step in `internal/provisioning/steps/` in the order that package declares,
and `--only` accepts those step names.

## Deploying to a device

Everyday deployment goes through the OTA release engine over Admin HTTPS;
SSH stays for first installation and repair.

```bash
make build
./internkim deploy --components admind,capabilityd
```

The rules that repay knowing before anything else:

- The device agent ships as `blueclawPayload`, with the pre-built artifact at
  `.dependency/blueclaw-payload/`. Any agent change
  needs `make prepare-blueclaw-payload` first; the deploy fails loudly when
  the artifact's revision does not match the submodule's HEAD.
- A new component takes two deploys because
  the release is applied by the `admind` already running: deploy `admind`,
  then the component.
- A running process keeps the configuration it started with. Shipping
  the writer of a config without the reader leaves the reader on the old
  file until it restarts; ship them in the same release.
- `systemctl is-active` confirms that the unit is running. After a deploy that
  changes agent input, check for a task run newer than the deploy.
- `./internkim release publish` pushes a stable channel to R2 for several
  devices to pull with `./internkim update`.
- Without `--components`, `deploy` rebuilds stale artifacts and ships every
  component that differs from the device, with its protocol partner. It refuses a
  component the device is ahead on, and `--plan` prints the selection without
  publishing.

The gate before any device deployment is the disposable local fleet, an ARM
Linux VM on macOS running the current checkout against real service
boundaries: `./internkim dev fleet run`. After deploying: `./internkim status`
and `./internkim verify api`.

## Reaching a device

The product opens no way in: `admind` listens on loopback and the agent's
connections are outbound. An operator on the same network needs nothing; from
elsewhere, a `ProxyCommand` in your own `~/.ssh/config` is the whole
arrangement, exactly as for [the host](/docs/architecture#why-the-host-has-no-inbound-port).
