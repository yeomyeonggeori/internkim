# Mobile app shell

## Goal

One app in the App Store and Play Store opens the company plane. A member
installs it, signs in with the account they already have, and sees their own
company: the same screens the web app serves, with nothing redrawn. Phone
features the web cannot reach (push through APNs and FCM, a home-screen
widget, clock-in by location) attach to that shell later, one plugin at a time.

## Why a shell

The web app is 604 Svelte components across 22 pages. A native-UI framework
(React Native, Flutter, Svelte Native) draws screens from its own widgets and
reads none of that HTML, so choosing one means rebuilding every screen and then
maintaining two of each. Svelte Native additionally has no Svelte 5 support,
which the app is written in.

Capacitor keeps the web app as the app and adds a bridge to the phone. Tauri
does the same job for the desktop and already lives in this repository as
`companion/`; it is the answer if a desktop shell is ever wanted, and it stays
as it is.

## Shape: the shell opens the zone

The shell does not bundle the screens. It opens `https://intern.kim`, the one
address every company signs in at, and everything behind that address keeps
working unchanged:

- `hooks.server.ts` injects the central plane into `#central-plane`, so the
  page knows its Supabase project the same way it does in a browser.
- `invokeTool` posts to the relative `/api/v1/...`, which resolves against the
  zone.
- A web deploy changes the app on the next open; no store release is needed
  for a screen change.

The cost is that the first screen needs a network, which the product needs
anyway. Capacitor's own documentation describes `server.url` as a live-reload
setting it does not recommend for production; it is used here because the
alternative is bundling the screens, which would retire `hooks.server.ts`,
turn every `/api/v1` call absolute, and put each screen change through store
review.

A company that self-hosts runs the whole stack at its own zone, and builds its
own app the same way: the zone is one value in `capacitor.config.ts`, chosen
at build time like `CLOUDFLARE_DOMAIN` is for the web app.

## Where it lives

```
web/
  capacitor.config.ts    appId kim.intern.app, server.url https://intern.kim
  app-shell/index.html   the empty webDir Capacitor insists on; never shown
  ios/                   generated by `cap add ios`, committed
  android/               generated by `cap add android`, committed
```

The config also sets `ios.contentInset` to `always`. Safari lays a standalone
PWA out below the status bar on its own; the WebView covers the whole screen,
and this inset is what keeps the page header from sitting behind the clock.

The status bar takes the page's colour from the page itself. Inside the shell,
`web/src/lib/native-shell/page-theme.ts` watches the `dark` class on `<html>`
and hands the computed body background and the tone to a `PageTheme` plugin
that each shell carries (`PageThemePlugin.java`, `PageThemePlugin.swift`), so
the bar follows the page's own theme switch and the system switch alike. The
Android theme still names a day/night colour pair for the moment before the
page runs, and `android-status-bar-colour.test.ts` keeps that pair equal to
the web app's `--background` tokens.

Everything sits under `web/` because plugins are imported from web code
(`subscribe.ts` will import `@capacitor/push-notifications`), and Capacitor
resolves plugins from the same `package.json` the native projects belong to.

`ios/` and `android/` are committed. They carry the signing identity, the
capabilities switched on in Xcode, and the manifest entries a plugin needs;
regenerating them loses that.

`kim.intern.app` is the identifier. The companion holds `kim.intern.companion`,
and the two must never collide in a keychain or a store listing.

## Signing in

The existing gate (`web-auth-gate.svelte`) is the sign-in screen. Email and
password always show. The passkey button shows whenever the WebView reports
`PublicKeyCredential`, and iOS's WebView reports it while refusing the call
until the zone is an associated domain, so in the shell the button shows and
fails. The password path stands, and the association is item 3 below.

Supabase keeps the session in `localStorage`, which both WebViews persist
across launches. The Buzz secret is claimed from the company's machine after
sign-in (`buzz-identity-central-login.ts`), which is browser-agnostic.

## Acceptance

The shell is done when all of these hold on a real phone:

| Check | Passes when |
| --- | --- |
| Load | The app opens on the `intern.kim` sign-in screen |
| Sign in | Email and password lead to the member's own company |
| Session | Closing and reopening the app keeps the member signed in |

Passkey is observed and recorded, and its outcome does not gate the shell:
either it works, or the button is hidden.

## What follows, in order

1. Push. `push_device.kind` already distinguishes device kinds. The edge
   senders in `supabase/functions/_shared/` grow an APNs and an FCM sender
   beside `web-push.ts`, keyed from the vault the way VAPID is, and
   `subscribe.ts` registers through `@capacitor/push-notifications` when
   `Capacitor.isNativePlatform()`.
2. Store listing. Icons, screenshots, privacy labels, TestFlight and the
   Play internal track first. Apple's guideline 4.2 refuses an app that only
   wraps a site, so push lands before the first submission.
3. Passkey association. `web/static/.well-known/apple-app-site-association`
   and `assetlinks.json`, plus Associated Domains on the iOS target, for the
   single zone. The first run on a phone showed the WebView refusing the
   passkey call without it.
4. Widget. A WidgetKit and App Widget target reading shared storage the web
   writes through a bridge plugin.

## Verification

```
cd web
bun add @capacitor/core && bun add -d @capacitor/cli
bunx cap init internkim kim.intern.app
bunx cap add ios && bunx cap add android
bunx cap open ios      # run on a device from Xcode
bunx cap open android  # run on a device from Android Studio
```

Then the three checks in the table, on both platforms, with the passkey
outcome noted alongside. `tools/verify` gains no group from this: the shell
has no tests of its own until push adds code to `web/src`.
