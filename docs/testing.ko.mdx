모든 변경은 세 가지 테스트로 확인합니다. 테스트마다 답하는 질문이 하나라서, 새
테스트가 들어갈 곳도 하나로 정해집니다.

| 종류 | 질문 | 위치 |
| --- | --- | --- |
| 유닛 | 로직이 맞는가 | `web/tests/unit/`, 소스 옆의 Go `_test.go`, `.dependency/internkim-plugin/tests/` |
| API | 라우트가 실제 데이터베이스에서 맞게 답하고, 막아야 할 것을 막는가 | `web/tests/api/`. 릴레이의 파일 옮기기는 `web/tests/transfer/`, 게이트웨이를 거치는 네이티브 앱과 작업 큐는 `web/tests/messenger-gateway/` |
| UI | 사람이 화면에서 일을 끝까지 할 수 있는가 | `web/tests/ui/<영역>/` |

에이전트 루프와 설치된 호스트에는 따로 관문이 있고, [아래](#the-agent-and-the-host)에
설명합니다.

## 새 테스트는 어디에

함수로 부를 수 있는 로직은 유닛 테스트입니다. 로직이 Svelte 컴포넌트 안에 있으면
먼저 함수로 꺼내고 그 함수를 테스트합니다.

라우트, 도구, 권한은 API 테스트입니다. API 테스트는 시드된 구성원으로 로그인해
브라우저가 부르는 방식 그대로 라우트를 부릅니다. 그래서 답을 확인하는 호출이 행
수준 보안도 함께 확인합니다.

화면은 그 라우트 이름의 폴더에 두는 UI 테스트입니다. `/crm`이면
`web/tests/ui/crm/`입니다. 내비게이션 레일이나 작업 공간의 로딩 상태처럼 한
라우트에 속하지 않는 화면은 `web/tests/ui/shell/`에 둡니다. 사람이 실제로 만나는
상태를 빠짐없이 확인합니다. 로딩, 빈 화면, 오류, 권한 없음, 휴대폰 폭입니다.
화면 폭은 `web/tests/ui/support/screen-widths.ts` 한 곳에 이름이 있습니다. 상태는
데스크톱과 휴대폰인 `everyScreen`에서 확인합니다. 레이아웃이 맞는지가 주제인
스펙은 breakpoint가 나누는 구간마다 가장 좁은 폭인 `everyLayoutBand`에서
확인합니다.

UI 테스트는 화면을 조작하고 화면에 보이는 것을 확인합니다. 앱 모듈을 페이지 안으로
import하지 않습니다. 그렇게 확인하고 싶은 로직은 그 모듈의 unit 테스트입니다.

화면이 어떤 plane에 붙는지는 파일 이름이 정합니다.

| 이름 끝 | 앱이 대화하는 곳 | 이럴 때 씁니다 |
| --- | --- | --- |
| `-central.spec.ts` | `supabase/seed.dev.sql`로 초기화한 로컬 Supabase | 화면이 기록을 읽거나 씁니다 |
| `-fixture.spec.ts` | 테스트가 `page.route`로 직접 답하는 주소 | 응답을 붙잡아 두거나 정확한 모양으로 줘야 합니다 |
| `-mocked.spec.ts` | 개발 서버의 샘플 데이터(`VITE_MOCK_*`) | 호스트가 답하는 화면이고 샘플 데이터로 충분합니다 |
| `.spec.ts` | central plane 없음 | 메신저처럼 plane 없이도 동작하는 화면입니다 |

central, fixture, standalone plane은 앱을 한 번 빌드해 `vite preview`로 띄운 곳에서
돕니다. 그래서 테스트는 사람이 받는 것과 같은 번들 CSS와 JavaScript를 만납니다.
mocked plane은 샘플 데이터가 있는 개발 서버에서 돕니다. 실행이 고른 project의
서버만 뜹니다.

`-central` 스펙을 돌리는 워커는 저마다 자기 회사로 로그인합니다. 그 회사는
`supabase/seed.dev.sql`이 워커마다 하나씩 만든 예시 회사의 사본입니다. 한 워커가
돌리는 스펙끼리는 그 회사를 같이 쓰므로, 회사 상태를 바꾼 테스트는 `afterAll`에서
되돌립니다.

같은 사실이 두 곳에 적혀 있을 때 둘이 어긋나지 않게 하거나 저장소 전체 규칙을
지키려고 소스 파일을 읽는 테스트는 가드입니다.
`web/tests/conventions/`에 두고 유닛 테스트와 함께 돌립니다.

## 언제 무엇이 도는가

`tools/verify`가 변경이 건드린 곳을 읽고, 그 변경이 깨뜨릴 수 있는 것을 돌립니다.

- 타입 검사와 유닛 테스트는 모든 웹 변경에 돌고, 빌드는 라우트 파일이나 빌드
  설정이 바뀔 때 돕니다.
- 로컬 plane이 필요한 테스트는 plane을 한 번 띄우고 한 번 초기화해서 함께
  씁니다. `supabase/tests/`의 데이터베이스 테스트는 `supabase/` 아래가 바뀔 때, API 스위트는 스키마,
  API 라우트, 서버 코드, 또는 그 스위트가 가져오는 파일이 바뀔 때 돕니다.
- UI 테스트는 `tools/verify --ui <영역,...>`으로 이름을 댄 영역만 돕니다.
  변경한 사람이 diff를 읽고 그 변경이 깨뜨릴 수 있는 화면의 영역을 고르며, 어느
  영역을 왜 돌렸는지 풀 리퀘스트에 적습니다. 웹 변경을 `--ui` 없이 돌리면
  `ui not run`을 출력합니다.

`tools/verify --plan`은 돌리지 않고 무엇을 돌릴지만 보여 주고,
`tools/verify --all`은 전부 돌립니다.

Go 테스트, 웹 스위트, UI 테스트처럼 모든 코어를 쓰는 그룹은 그 머신의 모든
`tools/verify`가 함께 쓰는 슬롯 하나를 잡고 돕니다. 슬롯은 코어 여섯 개마다
하나입니다. 여러 체크아웃이 동시에 verify를 돌리면 이 그룹들은 `wait`를 출력하고
슬롯을 기다리므로, 한 실행의 부하가 다른 실행의 시간 초과가 되지 않습니다.

한 번 통과한 그룹은 그 그룹의 패턴이 고르는 파일, 서브모듈 커밋, 도구 버전,
명령이 모두 같으면 다시 돌지 않습니다. 이 기록은 머신 전체가 함께 쓰므로, 새로
만든 clone이나 그 그룹의 파일을 건드리지 않은 rebase에서는 그 그룹이 `same`을
출력하고 넘어갑니다. 실패는 기록하지 않고, `--all`과 `--only`는 이름 붙인 그룹을
새로 돌립니다. 그래서 그룹의 패턴은 그 그룹이 읽는 파일을 빠짐없이 적어야 합니다.

## 직접 돌리기

```bash
cd web
bun run test                       # 유닛과 conventions
bun run test:api                   # API, 이 체크아웃으로 초기화한 로컬 plane에 대고
bun run test:ui                    # UI 전부
bun run test:ui tests/ui/crm       # 한 영역
go test ./...                      # Go, 저장소 루트에서
.dependency/internkim-plugin/tests/run
```

API 테스트와 `-central` UI 테스트는 `tools/with-local-plane`으로 로컬 plane을
잡습니다. plane이 꺼져 있으면 켜고, 다른 체크아웃이 쓰고 있으면 차례를 기다립니다.

## 에이전트와 호스트 [#the-agent-and-the-host]

| 관문 | 질문 | 비용 |
| --- | --- | --- |
| `./internkim dev simulate --scenario <name>` | 대본을 읽는 모델을 상대로 에이전트 루프가 맞게 결정하는가 | 몇 초 |
| `./internkim dev plane` | Linux에서의 시작, 요청자의 기억, 메시지, 공개 API가 동작하는가 | 몇 분 |
| `tools/test-native-install` | 설치된 회사 호스트가 메신저까지 포함해 업그레이드와 복원을 거쳐도 Linux에서 동작하는가 | 15분쯤 |
| `./internkim dev fleet run --scenario workspace-ownership` | POSIX 헬퍼가 요청자를 자기 워크스페이스 안에 묶어 두는가 | 몇 분 |

시나리오는 `BuiltinScenario`
(`.dependency/blueclaw/internal/defaultharness/e2e/virtual_session.go`)에
등록되어 있고, blueclaw나 스킬이나 capability 카탈로그가 바뀌면 `tools/verify`가
돌립니다. `dev plane`은 실제 POSIX 헬퍼를 갖춘 일회용 Linux VM에서
`web/tests/plane/`을 돌리고, 뒤에 붙인 인자는 테스트 실행기에 넘깁니다. 설치
리그와 fleet은 일회용 게스트를 쓰고 손으로만 돌립니다.

## 엔드투엔드

엔드투엔드 과제는 구성원이 에이전트에게 보내는 메시지 하나와, 그 뒤 기록과 파일과
다른 사람의 받은편지함에 남은 것입니다. 과제는 `web/tests/e2e/tasks/`에 한 파일씩
있고, 누가 보내는지, 지시, 에이전트가 멈춰서 물으면 그 스레드에 달 대답, 판정 항목,
끝난 뒤 지울 행을 적습니다. `tools/test-e2e`가 과제마다 그 구성원으로 설치된 회사
호스트에 메신저로 보내고 `web/tests/e2e/judge-delivery.ts`로 판정합니다.
`web/tests/pilot/`의 모델 파일럿도 같은 과제를 읽습니다.

```bash
internkim release packages --format deb --architecture arm64
monkeys run @test tools/test-e2e --only remote-work-clock-in
```

처음 실행하면 일회용 Linux 게스트에 패키지를 설치하고 시드 회사를 붙이느라 15분쯤
걸립니다. 게스트는 남겨 두므로 다음 실행부터는 바로 과제를 보냅니다. 새 패키지를
시험할 때는 `--fresh`, 게스트를 내릴 때는 `--remove`를 붙입니다. 과제마다 모델 호출
비용이 들어서 UI 영역처럼 골라 돌립니다. 프롬프트, 툴, 에이전트 런타임을 바꾼 변경은
그 변경이 깨뜨릴 수 있는 과제를 돌리고 어느 것을 돌렸는지 풀 리퀘스트에 적습니다.
에이전트가 만든 결과물은 `.artifacts/e2e/deliveries/<과제>/`에 남습니다.

## 속도 재기 [#measuring-speed]

`web/scripts/measure-navigation.ts`와 `web/scripts/measure-task-restart.ts`는
일회용 로컬 기록을 상대로 앱의 시간을 잽니다. 원격 주소는 거부하고, 자기가 만든
fixture는 지웁니다. 한 번 실행할 때 두 빌드를 번갈아 돌리고, 준비 실행 한 쌍은
빼고, 브라우저 작업은 한 번에 하나만 돌리며, 표본 수·중앙값·범위 곁에 빌드,
브라우저, 화면 크기, CPU 배율, 머신의 부하를 적습니다. 타이머는 테스트가 만든
카드나 새 응답 표식에서 멈춥니다. CPU를 제한한 휴대폰 폭은 휴대폰을 흉내 낼
뿐이고, 실제 휴대폰에 대해서는 아무것도 말하지 않습니다.

## 모델 평가

실제 모델에 묻는 테스트는 평가입니다. 품질을 재고, 돈이 들고, 릴리스 전에
돌립니다. 그래서 어떤 변경도 평가 때문에 머지를 기다리지 않습니다.
`llmeval` 태그로만 빌드되며, 태그를 켜고 빌드하는 것이 곧 돌리라는 요청입니다.
그래서 키나 서버가 없으면 건너뛰지 않고 실패합니다. 돌릴 평가는 `-run`으로
고릅니다.

```bash
monkeys run @test go test -tags llmeval -run OpenRouterLive ./internal/llmbackend
```
