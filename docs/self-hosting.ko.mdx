회사는 김인턴을 원하는 만큼 직접 운영하고 나머지는 `intern.kim`에 맡길 수 있습니다.
아래 단계는 흔히 멈추는 지점을 이름 붙인 것입니다.

| 단계 | 호스트 | Supabase | Cloudflare | 다른 네트워크에서 접속 |
|---|---|---|---|---|
| 1 | 내 컴퓨터 | `intern.kim` | `intern.kim` | 아니요 |
| 3 | 내 컴퓨터 | 직접 운영 | 직접 운영 | 아니요 |
| 4 | 내 컴퓨터 또는 클라우드 서버 | 직접 운영 | 직접 운영 | 예, SSH로 |

## 1단계: 내 컴퓨터에 호스트

회사가 계속 켜 두는 컴퓨터(김미니, Mac, Linux 컴퓨터 등)에 [호스트](/docs/running-the-host)를
설치합니다. 회사 기록, 웹 앱, 로그인 주소는 `intern.kim`에 있습니다. 호스트는
바깥으로만 연결하고, 회사에 연결된 뒤로는 로컬 인터페이스 밖에서 아무것도 요청을
받지 않으므로 컴퓨터에 공개 주소가 필요 없습니다.

## 3단계: 직접 운영하는 Supabase와 Cloudflare

회사 기록이 직접 운영하는 Supabase 프로젝트로 옮겨 가고, 웹 앱은 내 Cloudflare 계정에
배포해 `CLOUDFLARE_DOMAIN`이 가리키는 내 도메인으로 서비스합니다. 웹 앱을 직접 배포하기
때문에 웹 앱이 내 프로젝트의 주소와 키를 설정에서 읽을 수 있습니다. 그 프로젝트가 어떤
데이터를 갖는지는 [무엇이 어디에 있는가](/docs/what-lives-where)에 있습니다. 셀프호스팅
Supabase도 같은 Postgres와 같은 row level security를 제공하므로 `supabase/migrations`의
스키마가 그대로 적용됩니다.

모두가 내 도메인 자체에서 로그인하므로 로그인과 웹 앱은 더는 `intern.kim`에 기대지
않습니다. `install.sh`도 내 웹 앱이 내려주지만, 그 스크립트가 설치하는 호스트 패키지는
여전히 저희 GitHub 릴리스에서 받습니다.

### 웹 앱 배포

웹 앱이 어느 Supabase 프로젝트와 통신할지는 실행할 때 정해집니다. `hooks.server.ts`가
`SUPABASE_URL`과 `SUPABASE_PUBLISHABLE_KEY`를 페이지에 주입하고, 값은
`$env/dynamic/private`로 읽습니다. 그래서 빌드 하나가 어느 회사에나 쓰입니다. Pages
프로젝트에는 `tools/environment.json`이 `isRequiredOnPages`로 표시한 변수가 모두 있어야
하고, `web/scripts/set-pages-secrets.ts`가 그 변수를 전부 시크릿으로 넣습니다.

그중 `SUPABASE_JWT_SIGNING_KEY`는 웹 앱이 개인 액세스 토큰, 에이전트 세션, 호스트
세션에 서명하는 개인 키입니다. `web/scripts/issue-record-signing-key.ts`가 키를 만들어
출력하면, Supabase 대시보드의 Project Settings → JWT Keys에서 대기 키로 가져오세요.
그래야 프로젝트가 앱이 서명한 토큰을 검증합니다.

프로덕션 배포는 먼저 Supabase CLI로 `supabase/migrations`의 마이그레이션이 프로젝트에
모두 적용됐는지 확인합니다. 배포 전에 본인 계정으로 `supabase login`을 하고
`supabase link --project-ref <ref>`를 실행하세요. 프로젝트 키와 함께 보관하는 Supabase
액세스 토큰은 없습니다.

그래서 배포 순서는 하나입니다. `supabase db push`, 웹 앱, 그다음 엣지 함수와 게이트웨이
순입니다. 마이그레이션은 이전 웹 앱이 아직 돌고 있어도 성립하도록 씁니다. 세션에 더 많은
것을 요구하는 마이그레이션은 그 전에 발급된 세션을 만료될 때까지 받아 줍니다.

```bash
cd web
bun install
bun run build
bun run scripts/deploy-pages.ts --project <your-pages-project> --output .svelte-kit/cloudflare --production
```

스크립트는 `CLOUDFLARE_API_TOKEN`과 `CLOUDFLARE_ACCOUNT_ID`를 읽고, `--production`을
주지 않으면 프리뷰로 배포합니다. 커스텀 도메인은 항상 프로덕션 배포를 서비스하므로 프리뷰는
`*.pages.dev`에서만 응답합니다. Pages 커스텀 도메인은 와일드카드를 받지 않으므로 호스트명은
`scripts/pages-domains.ts`로 하나씩 연결합니다.

- 공개 값까지 모든 Pages 변수를 시크릿으로 저장하세요. `wrangler pages deploy`는 평문
  변수를 자기 설정에서 다시 써 넣기 때문에, 평문 값은 그 값을 쓰기 시작하려던 배포에서
  사라질 수 있습니다.
- `api.<zone>`은 같은 프로젝트에 연결합니다. 공개 API가 같은 라우트이기 때문입니다.
- `GATEWAY_URL`과 `GATEWAY_ADMIN_TOKEN`이 있어야 API 호출이 연결 게이트웨이를 거쳐 회사
  컴퓨터에 닿습니다. 없으면 호출은 `503`으로 답하고, 카탈로그와 토큰은 그대로 동작합니다.
- 구성원이 Buzz 데스크톱 앱이나 폰 앱을 쓰는 회사는 메신저 주소 `<slug>.<zone>`을
  게이트웨이의 Workers 라우트로 줍니다. 그 호스트명은 메신저의 것이고 Pages에 연결하지
  않습니다. 릴레이가 `/api/` 아래에 자기 경로를 갖고 있기 때문입니다. 브라우저로 그 주소를
  열면 여전히 `308`로 존 주소로 보냅니다. 게이트웨이는
  `web/scripts/deploy-worker.ts workers/connection-gateway --route-subdomain <gateway> --route-subdomain <slug>`로
  배포하고, 배포가 라우트 목록을 통째로 바꾸므로 남길 라우트를 모두 적습니다.
- `supabase config push`는 `config.toml` 전체를 보내므로 파일에 없는 설정은 CLI 기본값으로
  돌아갑니다. 종료 코드를 믿기 전에 출력되는 diff를 읽으세요.

## 4단계: 어느 네트워크에서든 SSH로 접속

호스트는 여전히 들어오는 길을 열지 않고, 제품도 그런 길을 제공하지 않습니다. 4단계의
회사는 컴퓨터로 가는 길을 스스로 고릅니다.

- 내 계정의 Cloudflare Tunnel과 그 앞의 Access 정책. 한 번만 접속할 때는
  `trycloudflare.com`의 임시 터널
- 공개 주소가 이미 있는 클라우드 서버에 올린 호스트

터널이나 서버는 운영자의 것입니다. [다른 호스트](/docs/architecture#why-the-host-has-no-inbound-port)와
마찬가지로 `~/.ssh/config`가 그 길을 가리킵니다.

## 레거시 디바이스 경로

회사별 어플라이언스는 레거시 디바이스 경로이며, [해당 페이지](/docs/device)가
설명합니다. 단계가 아니고, 더는 이것을 대상으로 새로 설계하지 않습니다.
