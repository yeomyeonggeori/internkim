## 도구 목록 [#listing-tools]

```bash
curl https://api.intern.kim/v1/tools \
  --header "Authorization: Bearer $INTERNKIM_TOKEN"
```

응답은 `{"tools": [...]}`이고, 키의 권한으로 부를 수 있는 모든 도구의
디스크립터 전문과, 어느 목록을 받았는지 말하는 `catalog` 필드가 담깁니다. 기본
카탈로그는 회사 머신에 묻지 않고 답하므로 빠르고 모두에게 같습니다. 같은 내용이
[도구 카탈로그](/ko/docs/tools/catalog)에도 정리돼 있습니다. 어떤 도구가 지금
실행 가능한지는 그 머신만 알고, 컴패니언과 함께 생겼다 사라지는 도구는 기본
목록에 아예 없습니다. 그건 `?live=true`로 물어야 하고 왕복 비용이 듭니다. 두 응답
모두 `X-INTERNKIM-CATALOG`에 `base`를 담습니다.

## 디스크립터 읽기 [#reading-a-descriptor]

```bash
curl https://api.intern.kim/v1/tools/task_add \
  --header "Authorization: Bearer $INTERNKIM_TOKEN"
```

토큰이 부를 수 없는 도구는 여기서 `404`로 답합니다. 없는 것처럼 보입니다.
호출 전에 읽어 둘 디스크립터 필드는 다음과 같습니다.

| 필드 | 말해 주는 것 |
|---|---|
| `inputSchema` | `input`이 만족해야 하는 JSON Schema |
| `outputSchema` | 성공 시 `result`의 모양 |
| `sideEffectClass` | 호출에 필요한 권한 |
| `idempotency` | 이 도구에서 `idempotencyKey`가 의미가 있는지 |
| `resultContract.effects` | 성공한 호출이 약속하는 `effects` 항목 |
| `availability` | 지금 실행 가능한지, 아니라면 왜인지 |

## 호출 [#invoking]

```bash
curl https://api.intern.kim/v1/tools/task_add/invoke \
  --header "Authorization: Bearer $INTERNKIM_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{"input":{"title":"분기 보고서 초안","size":"M"}}'
```

본문에는 `input`을, 지원하는 도구라면 `idempotencyKey`를 담습니다. `actor`나
`context`에 무엇을 보내든 admind가 도구를 부르기 전에 토큰의 것으로
덮어써집니다. `TestPublicToolGatewayOverridesActorFromBearerToken` 테스트가 이
동작을 고정하고 있습니다.

`input`은 무엇이 실행되기 전에 그 도구의 `inputSchema`로 읽힙니다. 레코드가
답하는 호출이든 회사 컴퓨터로 실려 가는 호출이든 같습니다. enum 밖의 값,
스키마에 없는 필드, 빠진 필수 필드는 필드 이름과 함께 `400`으로 거절됩니다.

```json
{ "message": "input.size: Invalid option: expected one of \"XS\"|\"S\"|\"M\"|\"L\"|\"XL\"|\"XXL\"" }
```

<Callout title="승인 대기가 없습니다" type="warn">
메신저 대화에서 에이전트는 삭제나 발송 전에 멈춰 서서 묻습니다. 이 길로 오는
read가 아닌 모든 호출에는 이미 승인된 연속 실행 표시가 붙으므로, 같은 도구가
여기서는 즉시 실행됩니다. 토큰의 권한이 곧 동의입니다. `delete` 토큰은
묻지 않고 지웁니다.
</Callout>

## 응답 [#the-response]

기록 위에서 도는 도구(업무, 캘린더, 사람, 연차, 근태)는
`{ "tool": ..., "result": ... }`를 답합니다. 평면이 직접 실행했기 때문입니다.
근태 쓰기는 여기에 `notified`가 하나 더 붙어, 누구에게 알렸는지 또는 어느
관리자에게 물었는지를 말합니다. `task_add`가 그중 하나입니다.

```json
{
  "tool": "task_add",
  "result": {
    "taskID": "b2c0…",
    "content": "분기 보고서 초안",
    "ownerID": "8f31…",
    "ownerName": "이샘플",
    "participantIDs": ["8f31…"],
    "participantNames": ["이샘플"],
    "participantPresentations": [
      {
        "personID": "8f31…",
        "displayName": "이샘플",
        "email": "sample@example.com",
        "mention": "@이샘플"
      }
    ],
    "business": "영업",
    "type": "",
    "size": "M",
    "status": "planned",
    "startDate": "",
    "endDate": "",
    "weekCode": ""
  }
}
```

여기 있는 필드는 전부 그 도구의 `outputSchema`이고, 디스크립터가 그것을 싣고
있으며 기록의 답은 거기에 묶여 있습니다. 다른 필드는 실릴 수 없고, 기록의 답은
나가기 전에 그 스키마로 검사됩니다. 업무의 제목은 `content`이고, 업무에 딸린
사람은 세 갈래로 옵니다. 다룰 때 쓰는 `participantIDs`, 찍을 때 쓰는
`participantNames`, 부를 때 쓰는 `participantPresentations`입니다.


회사 컴퓨터로 실려 간 도구는 아래의 더 넓은 모양으로 답합니다.
`message_send`가 그중 하나입니다.

```json
{
  "provider": "internkim",
  "selectedBackend": "device",
  "toolName": "message_send",
  "outcome": "succeeded",
  "status": "sent",
  "effects": [
    { "objectType": "message", "effect": "sent", "id": "..." }
  ],
  "result": { "messageIDs": ["..."], "deliveryStatus": "sent" }
}
```

| 필드 | 뜻 |
|---|---|
| `provider`, `selectedBackend` | 어디서 실행됐는지: `device`, `companion`, `remote` |
| `outcome` | `succeeded`, `failed`, `denied` 중 하나 |
| `status` | 도구가 정의한 상태 문자열 |
| `effects` | 실제로 바뀐 것의 기록 |
| `result` | 도구의 출력. `outputSchema`를 따릅니다 |
| `isError`, `message`, `errorCode`, `failureStage` | 실패의 상세 |
| `retryable`, `safeRetry` | 재시도가 말이 되는지, 그리고 안전한지 |

## effects [#effects]

`effects`는 실제로 바뀐 것의 기록이고, 런타임이 도구의 result contract에서
만들어 적습니다. 각 항목은 `objectType`과 `effect`(`created`, `updated`,
`deleted`, ...)를 밝히고, `id`, `path`, `url` 중 하나로 대상을 특정합니다.
항목에 따라 `visibility`, `durability`, `filename`, `contentType`, `summary`가
붙습니다.

`effects`가 실린 호출은 결과 본문 대신 그것으로 확인합니다. 비어 있으면
아무것도 바뀌지 않은 것입니다. 기록 도구에는 `effects`가 없고, `result`가 답
전부입니다.

## 멱등성 [#idempotency]

`idempotencyKey`는 디스크립터의 `idempotency.supported`가 `true`인 도구에서만
효력이 있습니다. 기본 카탈로그에서는 `message_send`가 그렇고, 나머지 도구에서
이 키는 전달만 될 뿐 아무것도 바꾸지 않습니다. 에이전트 메시지에서는
[`messageID`가 중복 제거를 맡습니다](/ko/docs/api/agent#sending-a-message).

## 힌트로 대상 고르기 [#choosing-a-target-with-a-hint]

수정·삭제 도구에는 별도의 ID 파라미터가 없습니다. `task_update`와
`task_delete`는 `taskHint`를 받습니다. 정확한 task ID이거나, `task_list` 결과에
보이는 그대로의 정확한 현재 제목입니다. 바꾸려는 새 제목이 아닙니다. 사람 참조도
같은 방식입니다. `participantPersonHints`는 이름, `@handle`, 이메일을 받습니다.

서버는 사다리를 하나 오릅니다.

1. 정확한 식별자나 정확한 제목은 확정됩니다.
2. 하나만 품고 있는 제목은 확정됩니다. 대소문자와 띄어쓰기는 무시합니다.
3. 여럿이 품고 있는 제목은, 그중 정확히 하나가 부르는 사람 자신의 업무일 때만
   확정되고 그 밖에는 질문으로 돌아옵니다.
4. 아무것도 안 맞으면 가까운 것들을 찾아 질문으로 돌려줍니다.

세 번째 칸의 소유권은 힌트가 스스로 깨는 유일한 동점이고, 한 방향으로만
깨집니다. 부르는 사람이 소유한 업무 쪽이지 남의 업무 쪽이 아닙니다. 남의 것이 둘
남는 힌트는 질문입니다.

식별자는 절대 근사하지 않습니다. 한 글자 다른 ID는 오타가 아니라 지어낸
것입니다. 여러 행이 나눠 가진 식별자도, 예를 들어 로컬 파트가 같아 `@handle`이
겹치는 두 주소도, 첫 번째를 고르는 대신 질문이 됩니다. 가까움은 그 값이 실제로
틀리는 방식으로 잽니다. 이름과 핸들은 한두 글자, 주소는 로컬 파트나 도메인,
제목은 얼마나 많이 겹치는지로 재기 때문에, 철자를 틀리면 아무것도 없다가 아니라
가장 가까운 이름들이 돌아옵니다.

확정되지 않은 힌트는 `409`로 답합니다.

```json
{
  "error": "박 matches more than one person",
  "errorCode": "interaction_required",
  "failureStage": "target_resolution",
  "retryable": true,
  "safeRetry": true,
  "hint": "박",
  "candidates": [
    { "id": "8f31…", "label": "박예시", "email": "yesi@example.com", "handle": "@yesi" }
  ]
}
```

누구를 말한 것인지 사람에게 물어야 하면 `errorCode`는 `interaction_required`이고,
아무것도 가깝지 않으면 `task_not_found`, `calendar_event_not_found`,
`person_not_found`, `task_participant_not_found` 중 하나입니다. 후보는 재시도에서
하나를 정확히 지목할 수 있도록 신원을 싣습니다. 후보의 `handle`은 다음 힌트가
그대로 받는 값이고, 도구 결과에 실리는 사람의 `mention`은 메시지에 적어 넣는
`@이름`이라서, 둘은 철자가 다르고 서로 바꿔 쓸 수 없습니다. 후보는 최대 여덟
개까지 옵니다. 거절은 무엇을 말하라고 지시하지 않습니다. 문구는 부르는 쪽의
몫입니다.

## 처음부터 끝까지 [#end-to-end]

[토큰 발급](/ko/docs/api#getting-a-token)에서 받은 `write` 토큰으로:

```bash
curl https://api.intern.kim/v1/tools/task_add/invoke \
  --header "Authorization: Bearer $INTERNKIM_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{"input":{"title":"분기 보고서 초안","size":"M"}}'

curl https://api.intern.kim/v1/tools/task_update/invoke \
  --header "Authorization: Bearer $INTERNKIM_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{"input":{"taskHint":"분기 보고서 초안","status":"in_progress"}}'
```

첫 응답의 `result`에는 새 `taskID`와 `"status":"planned"`가, 두 번째에는
같은 `taskID`가 `"status":"in_progress"`로 담깁니다. 기록 도구에는 `effects`가
없으니, `result`로 다시 읽은 task 자체가 확인입니다. 지우려면 `delete` 토큰이
필요합니다.

```bash
curl https://api.intern.kim/v1/tools/task_delete/invoke \
  --header "Authorization: Bearer $INTERNKIM_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{"input":{"taskHint":"분기 보고서 초안"}}'
```

`write`뿐인 토큰이라면 이 호출은 평면을 떠나기도 전에 거부됩니다. 회사
컴퓨터에는 아무것도 닿지 않습니다.

## 구현 위치 [#where-it-is-implemented]

| 관심사 | 위치 |
|---|---|
| 목록·조회 핸들러 | `web/src/routes/api/v1/[...path]/+server.ts`의 `discoveryAnswer`, 바탕은 `web/src/lib/server/public-api/catalog.ts` |
| 호출 핸들러 | `internal/admind/public_tool_gateway.go`의 `invokePublicTool`. 회사 릴레이를 지나 닿습니다 |
| `capabilityd`에서 디스크립터 가져오기 | unix 소켓 너머의 `fetchCapabilityRegistry`; 기기와 컴패니언 디스크립터는 `exposableCapabilityDescriptors`에서 합쳐집니다 |
| actor 덮어쓰기 | `invokePublicTool`이 본문을 디코드한 뒤 `Actor`, `Context`, `PrivacyClass`, `RequiresUserPresence`를 다시 채웁니다 |
| 승인-연속 플래그 | `publicToolInvokeContext`, `publicToolPermissionForDescriptor`가 기준입니다 |
| 요청·응답 타입 | `pkg/capabilityprotocol/protocol.go`의 `ToolInvokeRequest`, `ToolInvokeResponse`, `ResourceEffect` |
| 입력·출력 스키마 | `pkg/capabilityprotocol/generated/capability-tools.json` |
