Every tool internkim uses inside a company is callable from outside it, over
HTTP, at `https://api.intern.kim/v1`. Every company we host calls that one
address; the token is what says which company, and which person inside it. A
company hosting internkim itself calls its own host at `/api/v1`, which is the
same API on the same code. A token belongs to a person and every call runs as
that person, so a token can never do more than its owner can.

The web app answers the request. It resolves the caller, then answers what it
knows: the tool catalog, the tokens a person holds, a file kept for a later
call, and every tool that reads or writes the record itself. What is left needs
the company's computer — the messenger, the workspace, the browser — so those
calls are carried there and the answer comes back.

## Getting a token [#getting-a-token]

The first token is made signed in, from the personal access tokens panel in
settings. It is shown once.

After that a token makes its own successors, so a script rotates one without a
browser:

```bash
curl -X POST https://api.intern.kim/v1/token \
  --header "Authorization: Bearer $INTERNKIM_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{"name":"reporting script","permission":"write"}'
```

```json
{ "name": "reporting script", "permission": "write", "token": "ik_..." }
```

`token` is answered once and only its SHA-256 hash is kept, so a lost token is
replaced rather than recovered. `permission` defaults to the rung the calling
token holds, and a token may never mint one that reaches further than itself.
`name` may be left out, and the token is called `pat-1`, `pat-2`, and so on by
the first ordinal the member does not already hold.

`GET /v1/tokens` lists the names and rungs the member holds, and is the only
plural path: `POST /v1/token` makes one and `DELETE /v1/token?name=<name>`
revokes one, because each acts on exactly one token.

## Rotating a token [#rotating]

A token cannot revoke itself, and that is what makes rotation safe: the
replacement has to answer before the token it replaces goes away.

1. `POST /v1/token` with the old token, naming the new one.
2. Call something with the new token and see it answer.
3. `DELETE /v1/token?name=<old>` with the new token.

Naming the presented token in either call answers `409`.

## Authentication [#authentication]

Every other endpoint takes the token as a bearer header:

```bash
curl https://api.intern.kim/v1/tools \
  --header "Authorization: Bearer $INTERNKIM_TOKEN"
```

The owner is re-resolved on every request. When the owner stops being active
member, every call with their token answers `403` from that moment on; nothing
needs to be cleaned up first.

A signed-in web session works the same way: the bearer may be the Supabase
access token of the session instead of an issued key. The session is the
person, so it carries full permission — the web app calls these endpoints with
it, and a script that already holds a session can too. Issued keys exist for
everything that should not hold a session: they name their own permission rung
and survive sign-out.

## Permissions [#permissions]

A token holds one permission, and there are three of them. Each reaches
everything below it, and what a tool needs comes from its `sideEffectClass`,
never from its name.

| Permission | Opens |
|---|---|
| `read` | tools whose `sideEffectClass` is `read` |
| `write` | those, plus every writing class: workspace writes, external edits and sends, publishing, connections, browser actions, and the [agent endpoints](/docs/api/agent) |
| `delete` | everything, including deletes |

The writing set is the list in `web/src/lib/server/public-api/catalog.ts`, and
a descriptor carrying a `sideEffectClass` that is not in it needs `delete` — in
the app that lists the tools and again on the machine that runs one. An
unrecognized class fails closed at both ends.

## Errors [#errors]

Success bodies are JSON. Error bodies are plain text, with two exceptions the
app answers as JSON: the catalog's own `{"error":"not found"}`, and a hint
refusal, which carries `hint` and `candidates` so the next call can name one.

Two machines answer, and they do not share their wording. The app answers
everything it resolves itself:

| Status | Body | When |
|---|---|---|
| `400` | decode error, `this call carried a body that is not a json object`, `input is the object the tool reads` | the body is not valid JSON, or a required field is missing |
| `401` | `sign in first` | no `Authorization: Bearer` header, or the token names no account |
| `401` | `that key belongs to nobody` | the `ik_` token is unknown or revoked |
| `403` | `refused` | the account signed in is a member of no company |
| `403` | `this token may only <permission>, and <tool> <permission>s` | the token's permission is below what the tool requires |
| `403` | `write permission required` | an agent endpoint with a read-only token |
| `404` | `{"error":"not found"}` | `GET /v1/tools/<name>` for a tool this token cannot see |
| `409` | `a token cannot revoke itself...` | `DELETE /v1/token` naming the token that authenticated the call |
| `409` | the hint refusal, with `hint` and `candidates` | a hint that matched nothing, or more than one thing |
| `500` | `the control plane is not configured` | the app is missing its Supabase settings |
| `502` | `the gateway answered <status>, and no status a caller can use` | the company answered with nothing a caller can use |
| `503` | `the company gateway is not configured` | an invocation where nothing knows how to reach the company |

A call carried to the company is answered by `admind`, in its own words:

| Status | Body | When |
|---|---|---|
| `401` | `bearer token required`, `invalid bearer token` | the company machine did not recognize the call |
| `403` | `token owner is not active member` | the owner left or was deactivated |
| `403` | `asserted requester is not active member` | the named requester is not a member |
| `403` | `tool is not available for this token` | an unknown tool, or one above the token's permission |
| `502` | whatever failed to resolve | the descriptor or the actor could not be read |

<Callout title="A departed owner's token answers 500" type="warn">
A token whose owner is `departed` or `withdrawn` should be refused where it is
resolved, and instead `sessionForMember` throws and the caller gets a `500`
with the thrown message. The company machine's `403` above is the only place
this is answered properly today.
</Callout>

## Keeping a file [#keeping-a-file]

`POST /v1/files` takes the bytes themselves, up to 25 MB, with the file's own
content type and an optional `?filename=`. The file is kept in the company's
store and materialised into the workspace, and the answer names the path a
later call can reach it by. A reading token is refused here, because keeping
bytes anywhere is a write.

## Revoking a token [#revoking-a-token]

`DELETE /v1/token?name=<name>` forgets the token by that name, and the next
call carrying it is refused. A token cannot revoke itself; revoke it with
whichever token replaced it.

## The served reference [#the-served-reference]

`docs.intern.kim/api` serves an interactive reference, in Korean or English,
rendered from an OpenAPI document at `docs.intern.kim/openapi/<language>.json`.
`/api-docs` and `/openapi/<language>.json` on any company host redirect there.
The base tools in that document are read from the same catalog the
agent runs on.

## Where it is implemented [#where-it-is-implemented]

The API is part of the web app, so a company that hosts the app hosts the API.
`api.<zone>/v1` and `<company host>/api/v1` are the same routes.

| Concern | Where |
|---|---|
| Routing for everything under `/api/v1` | `web/src/routes/api/v1/`; `/v1/*` is rewritten onto it in `web/src/hooks.ts` |
| Who is calling, from a session token or an `ik_` key | `callingMember` in `web/src/lib/server/member-request.ts` |
| Token issue, `ik_` format, SHA-256 hashing, store | `issuePersonalAccessToken` in `web/src/lib/server/control-plane.ts`; the rules in `web/src/lib/server/public-api/tokens.ts` |
| Permission rungs and the tools each reaches | `web/src/lib/server/public-api/catalog.ts`, over `web/src/lib/public-api-permission.ts` |
| Carrying a tool call to the company machine | `web/src/lib/server/public-api/company-call.ts`, through `workers/connection-gateway` to the company's relay |
| What the company machine does with it | `handlePublicAPI` in `internal/admind/public_tool_gateway.go`, then `invokeCapabilityTool` over the `capabilityd` socket |
| Agent endpoints | `internal/admind/agent_drive.go`, forwarding to Blueclaw through `blueclawJSONRequest` |
| Wire types | `pkg/capabilityprotocol/protocol.go` |
| Tool catalog | `pkg/capabilityprotocol/generated/capability-tools.json` |
| The contract, stated as tests | `web/tests/integration/public-api-route.test.ts`, `internal/admind/public_tool_gateway_test.go` |
| OpenAPI document and the `/api-docs` redirect | `docs/web/app/lib/openapi.ts`, `web/src/lib/server/api-reference-redirect.ts` |
