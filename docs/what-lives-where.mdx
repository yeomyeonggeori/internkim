One question decides it. If that computer burned down tonight, what has to
still be true tomorrow?

Whatever answers yes belongs in the record. Whatever is a fact about the
machine belongs on the host.

## The record

Every table here is something a company would still need after replacing every
computer it owns. `supabase/migrations` is the schema itself, one migration
per change, and [What the tables mean](/docs/record/schema) explains what
each table is for. Read the table list from the migrations rather than here, which drifts.

Calendar events are tasks with a span and `is_event`, which is why there is
no separate table for them. There is no table for a message, which is why no
conversation can reach the record.

Attachments and pictures the chat screen shows are copied into the company's
`asset` bucket in Supabase Storage, addressed by their content, so a browser
on another network can open them. The conversation they came from stays on
the messenger.

## The agent's store

The host's own Postgres, defined in `.dependency/blueclaw/migrations/`. It
needs the `vector` extension. The company host package installs and supervises
Postgres with the rest of the host services.

| | |
|---|---|
| Conversation | `raw_event`, `conversation`, `attachment`, `connector_outbox`, `live_reply_post` |
| Execution | `task_run`, `task_attempt`, `task_step`, `task_event`, `task_schedule`, `task_session`, `task_artifact`, `task_wait_token`, `morning_briefing_schedule` |
| Memory | `memory_episode`, `memory_fact`, `memory_fact_circle`, `memory_fact_embedding`, `memory_profile`, `memory_job` |
| Policy and identity | `person`, `person_email`, `platform_account`, `policy_channel_rule`, `policy_revision` |
| Operations | `admin_audit_log`, `backup_lock` |

None of it is a company record. It is the agent's working state: what was
said, what it did, what it remembers, and what it is allowed to touch.
`task_event` is the ledger the rest of the system trusts: every tool call,
its full input, and every routing decision land there, which is what makes a
failed run diagnosable after the fact.

The memory tables are [bluememo](https://github.com/yeomyeonggeori/bluememo)'s:
episodes of finished work, the facts a model extracted from them, the circles
each fact is shared with, the embeddings recall searches, and the jobs that
extract and condense.

## The relay's state

`RELAY_STATE_DIR`, `/var/lib/internkim/relay` unless set, holds what the relay
must survive a restart with: `inbound/`, the messages the agent has not taken
yet, and `questions/`, the approval questions still waiting for an answer.
Both empty themselves as the work moves on.

## Files

The workspace lives on the host, under the permissions described in
[Boundaries](/docs/boundaries). Private space per person, shared space per
circle, and a service-owned area the agent's own machinery uses. The skills
the agent loads ship in the package, from `.dependency/internkim-plugin/`, and
belong to no company.

Backing the host up is the company's job. Losing it loses the agent's memory,
its history, the files and any message still queued, and loses none of the
company's records. That asymmetry is deliberate: keeping the agent's memory
central would mean holding a company's internal knowledge on our side, the
thing this design avoids for messages and mail.
