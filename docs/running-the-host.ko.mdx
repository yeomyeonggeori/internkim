호스트는 켜 둔 컴퓨터 한 대입니다. 리눅스 서버든, 잠들지 않는 Mac이든, 구석의
작은 상자든요. 네트워크로부터는 바깥으로 나가는 회선 하나만 필요합니다.

## 기동 순서 [#the-boot-order]

`host/entrypoint.sh`가 번들을 띄우고, 그 순서가 곧 설계입니다.

<Steps>
<Step>
**릴레이**, 무엇보다 먼저, Postgres가 답하기도 전에. 뜨는 데 번들의 다른 무엇도
필요 없으므로, 아래 것들이 죽어 있거나 재시작 중이어도 채팅 화면은 계속 답하고,
그사이 도착한 메시지는 에이전트가 가져갈 수 있을 때까지 큐에서 기다립니다.
entrypoint는 릴레이가 어떻게 끝났든 5초 뒤 다시 띄웁니다.
</Step>
<Step>
**런타임과 명부.** `tools/render-company-runtime`이 이 컴퓨터의 주소들로
`runtime.template.json`을 채워 `/run/internkim/runtime.json`에 씁니다.
`/etc/blueclaw`에 `runtime.json`이 마운트되어 있으면 그것을 대신 읽습니다.
그 자리에 마운트된 `policy.json`은 `/run/internkim/policy.json`의 씨앗일 뿐
그 파일 자체가 아닙니다. 회사가 바뀔 때마다 admind가 그 파일을 다시 쓰기
때문이고, 파일에 쓸 수 없으면 부팅이 멈춥니다.
</Step>
<Step>
**Postgres 대기**: `DATABASE_URL`, 기억 검색이 쓰는 `vector` 확장을 갖춘
에이전트 자신의 저장소.
</Step>
<Step>
**`internkim-capabilityd`**, `/run/internkim/capability.sock`. entrypoint는 그
소켓을 기다리고, 소켓이 생기기 전에 데몬이 죽으면 포기합니다. 한번 뜬 뒤로는
아무도 다시 보지 않고, 번들을 내리는 것은 에이전트 자신의 종료뿐입니다. 모든
모델 호출과, 프로바이더 자격증명을 쥔 모든 도구가 여기를 거칩니다.
</Step>
<Step>
**에이전트**:

```
blueclaw -runtime /run/internkim/runtime.json -policy /run/internkim/policy.json \
  -acp-socket /run/internkim/blueclaw-acp.sock -inbound acp
```

`-inbound acp`는 메시지가 그 소켓으로, 릴레이에게서만 들어온다는 뜻입니다.
관리 API는 `127.0.0.1:8080`에 남고, entrypoint가 기다리는 것도 이 포트입니다.
스킬은 이미지가 internkim-plugin에서 채워 둔 `BLUECLAW_BUNDLED_SKILLS_PATH`에서
읽습니다.

이미지의 `blueclaw`는 시작하기 전에 `blueclaw` 사용자로 내려갑니다. 터미널이
root로는 실행을 거부하기 때문입니다. 그 사용자에게 `/root`는 닫혀 있으므로
entrypoint가 에이전트 키와 모델 키를 `/run/internkim/secrets`에 그룹 `blueclaw`,
모드 `0440`으로 복사해 둡니다.
</Step>
<Step>
**`internkim-admind`**, `127.0.0.1:18080`. 릴레이가 워크스페이스 호출을 전부
여기로 보냅니다. 에이전트 다음인 이유는, 시작하면서 회사 명부를 에이전트 위에
맞추는데 아직 뜨지 않은 에이전트에 맞추려 하면 다음 시도까지 2분을 기다리기
때문입니다.
</Step>
<Step>
**`internkim-maild`**, `127.0.0.1:18092`. 그다음 **커넥터**(`chatd`)가
`127.0.0.1:18090`에서, 봇으로 메신저에 로그인해 도착하는 메시지를 릴레이의
`/inbound`로 보냅니다.
</Step>
</Steps>

이 컴퓨터에 없어도 되는 것: Cloud Hypervisor, 자체 메신저, cloudflared. setuid
POSIX 헬퍼는 싣습니다. blueclaw는 헬퍼 없이도 `status: ok`로 부팅하고, 그다음
워크스페이스 도구를 모두 거부하기 때문입니다.

## 설정 [#settings]

entrypoint는 여섯 개의 값을 요구하고 나머지는 그대로 흘려보냅니다.

```
SUPABASE_URL=https://<project>.supabase.co
SUPABASE_PUBLISHABLE_KEY=<프로젝트의 publishable key>
INTERNKIM_APP_URL=https://intern.kim
CHATD_BOT_USER_NAME=<봇의 표시 이름>
MESSENGER_PLATFORM=buzz
DATABASE_URL=postgres://…
```

에이전트 키는 이 값들에 끼지 않습니다. `/root/.internkim/secrets/agent-key`에
모드 `0600`으로 놓인 파일이고, 경로로 읽히므로 `/proc`을 읽는 무엇이든 볼 수
있는 프로세스 환경에 남지 않습니다. 파일을 교체하는 것이 곧 키 교체 절차의
전부입니다. 모델 프로바이더의 키는 그 옆에 `openrouter-key`로 놓이고,
capabilityd도 경로로 읽습니다.

그리고 회사가 굴리는 메신저.

```
CHATD_BUZZ_RELAY_URL=wss://…  CHATD_BUZZ_PRIVATE_KEY=<64 hex>
```

그리고 릴레이가 앱에 답할 때 거치는 게이트웨이.

```
GATEWAY_URL=…            GATEWAY_SERVER_KEY=…
```

<Callout type="warn">
게이트웨이 설정 두 개가 없으면 릴레이는 그냥 뜨고, 그에 대해 아무것도 로그하지
않고, 앱에도 API에도 영원히 답하지 않습니다. 프로세스 표는 초록인데 메신저
화면이 비어 있는 것이 그 증상입니다.
</Callout>

릴레이와 번들이 읽는 나머지 설정은 기본값과 함께 `host/README.md`의 생성된 표에
있습니다. `RELAY_STATE_DIR`은 재부팅을 넘어 남는 디스크에 두세요. 에이전트가
아직 가져가지 않은 메시지 큐가 거기 삽니다.

`admind`가 없으면 어떤 사람의 기억, 파일, 실행, buzz 클레임이 `500`을 답합니다.
부탁한 사람의 이름으로 나가는 다이렉트 메시지는
`/root/.internkim/secrets/buzz-key-seed`의 시드로 서명됩니다. 그 파일이 없어도
이 컴퓨터는 부팅하며 그렇다고 알리지만, 그런 메시지는 보낼 수 없습니다.

Buzz로 채팅하는 회사는 Buzz 스택도 직접 굴립니다. `host/buzz/`에 Postgres,
Redis, MinIO, 그리고 Buzz 릴레이를 같은 기계에 올리는 compose 파일이 있습니다.

## 답은 얼마나 커도 되는지 [#how-big-an-answer-may-be]

전송로는 크기를 넘긴 프레임을 소리 없이 거절해 호출자를 영원히 기다리게
만듭니다. 그래서 릴레이는 모든 답을 먼저 재고, 호출자에게 실제로 닿는 바이트
수 명시 `413`으로 답합니다. 기본 상한은 3,000,000바이트입니다 (십진수이고
Supabase의 수치라서 `3 * 1024 * 1024`로 쓰면 145 KB를 넘칩니다).
`ANSWER_BYTE_CEILING`이 그 값을 덮어쓰고, 양수가 아닌 값은 모든 답을 소리
없이 거절하는 대신 부팅을 멈춥니다. 프로필 사진 한도는 base64가 3분의 1을
불리므로 상한에서 유도됩니다. 실제 상한은
`host/relay/measure-broadcast-ceiling.ts`가 프로젝트를 상대로 이진 탐색해
확정합니다.

## 계속 돌게 하기 [#keeping-it-running]

크래시나 재부팅 뒤에 돌아오도록, 번들을 그 컴퓨터에서 프로세스를 관리하는
무엇에든 맡기세요.

| | |
|---|---|
| systemd | `host/relay/internkim-relay.service` — 설정은 `/etc/internkim/relay.env`, `Restart=always` |
| launchd | `host/relay/launchagent.plist.template` — `KeepAlive` |
| 번들 | `entrypoint.sh`가 릴레이를 직접 띄우고 다시 띄움 |

죽고 돌아오지 않는 릴레이는 채팅 화면을 비워 두고 어떤 메시지도 에이전트에
닿지 못하게 하는데, 그것이 지킬 가치가 있는 실패입니다.

`make build-relay`는 릴레이를 단일 실행 파일 `internkim-relay`로 컴파일하므로
그 컴퓨터에 Bun도 `node_modules`도 필요 없습니다. `RELAY_TARGET`으로 크로스
빌드합니다 (`bun-linux-arm64`, `bun-linux-x64`, `bun-darwin-arm64`).
`make build-maild`가 메일 응답자를 같은 방식으로 빌드합니다.

## 정말 아웃바운드 전용인지 확인 [#checking-it-is-really-outbound-only]

```bash
ss -ltnp | grep -v '127.0.0.1\|::1'                     # 아무것도 출력되지 않음
systemctl list-units | grep -E 'cloudflared|stunnel'    # 아무것도 출력되지 않음
```

이 컴퓨터의 관리는 회사 자신의 방식대로입니다. 같은 네트워크에서의 셸이든,
다른 곳에서라면 자신의 `~/.ssh/config`에 넣는 `ProxyCommand`든. Cloudflare
Tunnel은 그 자리에 편리한 선택지이고 우리가 개발하며 쓰는 것이지만, 딱
그만큼입니다.
