회사 호스트는 arm64 또는 amd64의 Debian 13, Ubuntu 22.04 또는 24.04, Fedora,
RHEL 호환 10(Rocky, AlmaLinux), Arch Linux, 그리고 Homebrew를 설치한 Apple
실리콘 Mac에서 실행됩니다. Linux 패키지는 glibc 2.35 이상이 필요합니다. 인터넷에
연결하고 계속 켜 두어야 합니다. 설치 프로그램은 Linux의 systemd나 macOS의
launchd에 서비스를 등록합니다. 공개 주소, 외부에서 들어오는 포트, Docker 설치는
필요하지 않습니다.

## 설치하기

회사 설정 화면에서 연결 파일을 받은 다음 실행하세요.

```bash
curl -fsSL https://intern.kim/install.sh | sh -s -- host
sudo internkim install ~/Downloads/internkim-host.json
```

첫 명령은 apt, dnf, pacman 또는 Homebrew 패키지를 설치합니다. Linux에서는 이
컴퓨터에 맞는 패키지를 저희 GitHub 릴리스에서 받아 릴리스의 `SHA256SUMS`와
대조한 다음 패키지 관리자에게 넘깁니다. Mac에서는 저희 Homebrew 탭
`yeomyeonggeori/tap`을 추가하고 `internkim` formula를 설치합니다. 이 formula의
bottle은 같은 GitHub 릴리스에서 받고, formula에 적힌 체크섬과 대조합니다. 둘째 명령은 회사를 설정하고 OpenRouter
API 키를 받은 뒤 호스트 서비스를 등록합니다. 컴퓨터가 켜지면 서비스가 자동으로
시작하고, 서비스가 종료되면 다시 시작합니다. 설치는 모든 서비스가 응답하고
에이전트가 회사 명단을 받은 뒤에 끝나므로, 구성원은 바로 에이전트에게 말을 걸 수
있습니다. 그다음 화면에 나온 회사 설정 주소에서 연결 확인을 누르세요.

Linux에서는 연결 파일 없이도 됩니다. 첫 명령만 실행하면 컴퓨터는 회사를 기다리며
같은 네트워크의 `http://<컴퓨터>.local:18088/`에 8자리 연결 코드를 띄웁니다.
`sudo internkim box code`로도 같은 코드를 볼 수 있습니다. 같은 네트워크에 있는
관리자가 회사 설정 화면에 코드를 넣고, 컴퓨터 키의 마지막 네 글자를 확인한 뒤
연결을 누르면 됩니다. 그다음 설정 화면이 OpenRouter 키를 묻습니다. 연결이 어떻게
이뤄지고 연결 해제가 무엇을 되돌리는지는 [김미니](/ko/kim-mini)에 있습니다.

## 업데이트하기 [#updating]

호스트는 설치 프로그램을 다시 실행하거나 에이전트에게 부탁해서 업데이트합니다.

### 설치 프로그램으로

첫 명령을 다시 실행하세요. Linux에서는 채널이 지금 가리키는 릴리스를 지금 버전
위에 설치합니다. macOS에서는 Homebrew가 formula를 업그레이드하고 서비스를 새
버전으로 다시 시작하며, 그러려고 비밀번호를 묻습니다. 회사와 데이터는
그대로 남습니다. 기본 채널은 최신 정식 릴리스입니다. Linux에서
`--channel testing`은 사전 릴리스까지 포함해 가장 새 릴리스를 따라가고,
`--version`은 태그로 릴리스 하나를 설치합니다. 더 오래된 릴리스도 됩니다.

```bash
curl -fsSL https://intern.kim/install.sh | sh -s -- host --channel testing
curl -fsSL https://intern.kim/install.sh | sh -s -- host --version v2026.10.01.203142
```

설치 프로그램은 따라간 채널을 `/var/lib/internkim/release-channel`에 적어
둡니다. 탭에는 최신 정식 릴리스만 올라가므로 Mac은 기본 채널을 따라가고 버전을
고정할 수 없습니다.

### 에이전트에게 부탁해서

구성원은 누구나 호스트가 어떤 버전인지, 더 새 정식 릴리스가 나왔는지 물을 수
있습니다. 관리자는 에이전트에게 호스트를 업데이트하거나 이전 정식 릴리스로
되돌리라고 할 수 있습니다. 에이전트는 정식 채널로 설치한 Linux 호스트에서만,
그리고 관리자가 확인 질문에 답한 뒤에만 업데이트합니다. 질문에는 릴리스 노트,
재시작이 치르는 비용, 그리고 언제 할지가 들어갑니다. 지금, 회사 시간으로 새벽
3시, 또는 관리자가 말한 시각 중에서 고릅니다. 저절로 업데이트되는 일은 없습니다.

확인하면 root로 도는 관리 게이트웨이가 누가 어느 대화에서 부탁했는지 적어 두고,
설치 프로그램을 `--version`과 함께 별도 systemd 유닛 `internkim-host-update`에서
실행합니다. 이 유닛은 업데이트가 일으키는 재시작 뒤에도 남습니다. 업데이트가 도는
동안 두 번째 업데이트는 거절됩니다. 에이전트가 돌아오면 그 대화에서 호스트가
어느 버전이 되었는지, 또는 무엇이 실패했고 지금 어느 버전인지 답합니다.

### 재시작이 치르는 비용

회사에 연결된 Linux 호스트에서 업데이트는 처음 설치 때 쓴 설정을 다시 쓰고,
데이터베이스를 다시 준비하고, 서비스를 다시 시작한 뒤 모두 응답하고 에이전트가
명단을 다시 받았을 때 끝납니다. 에이전트, 릴레이, 메신저는 DOWNTIME_TEXT_KO
동안 멈춥니다. 그사이에 보낸 메시지는 전송에 실패하므로 다시 보내야 합니다.
재시작 순간 돌던 업무는 중단되었다가 에이전트가 돌아오면
한 번 이어서 실행됩니다. 이어서 실행할 수 없는 업무는 실패로 표시되고 요청자에게
알립니다. 업데이트 중에 시각이 된 예약 작업은 늦게 한 번 실행됩니다.

내려받기나 체크섬 확인이 실패하면 아무것도 설치되지 않고 호스트는 원래 버전에
남습니다. 설치는 되었지만 서비스가 돌아오지 않는 릴리스는 설치된 채 설정되지 않은
상태로 남고, 업데이트가 응답하지 않는 서비스와 이유를 읽는 방법을 알려 줍니다. 그
문제를 고친 뒤 `sudo internkim refresh`를 실행하면 같은 단계를 다시 밟고, 이전
태그로 `--version`을 주면 되돌아갑니다.

## 제거하기

```bash
sudo apt remove internkim     # Debian, Ubuntu
sudo dnf remove internkim     # Fedora, RHEL 호환
sudo pacman -R internkim      # Arch Linux
```

패키지를 제거하면 호스트 서비스가 멈추고 비활성화되며, 프로그램 파일과 호스트의
Python 런타임, 스킬을 위해 준비한 것이 지워집니다. 설치할 때 패키지 저장소나 서명 키는 추가하지 않습니다. 회사는
컴퓨터에 남습니다. `/var/lib/internkim`에는
호스팅 서비스에서 이 회사를 증명하는 키와 사람마다 메시지에 서명하는 시드가 있고,
`/var/lib/internkim-postgres`와 `/var/lib/internkim-cache`에는 호스트의 데이터베이스와
캐시가 있습니다. 패키지를 다시 설치하면 같은 회사로 돌아옵니다. Debian과 Ubuntu에서
`sudo apt purge internkim`을 쓰면 `/etc/internkim`의 설정도 지웁니다.

두 키는 다시 발급할 수 없으므로 회사를 지우는 일은 직접 하세요. 마지막
디렉터리에는 백업이 있습니다.

```bash
sudo rm -rf /var/lib/internkim /var/lib/internkim-postgres /var/lib/internkim-cache /var/lib/internkim-backups
```

## 서비스 확인하기

Linux에서는 systemd에서 상태와 로그를 확인합니다.

```bash
systemctl list-units 'internkim*' 'blueclaw*' 'buzz*'
systemctl status internkim-relay
journalctl -u internkim-relay -n 50 --no-pager
```

macOS에서는 `launchctl print system/kim.intern.<service>`로 서비스를 확인합니다.
로그는 `/var/log/internkim/`에 있습니다.

## 설정

설치 프로그램은 회사 연결 정보와 생성된 자격증명을 접근이 제한된 호스트 데이터
디렉터리에 저장합니다. 대부분은 이 파일을 직접 고칠 필요가 없습니다. 선택 설정은
`/etc/internkim/company-host.env`에 둡니다. 지원하는 변수와 기본값은 생성된
[호스트 설정 참조](https://github.com/yeomyeonggeori/internkim/blob/main/host/README.md)에
있습니다. API 키와 연결 파일은 설정 파일에 넣지 마세요.

## 로컬 데이터

회사 컴퓨터에는 에이전트의 대화와 업무 이력, 기억, 워크스페이스 파일, 전달 대기
메시지가 저장됩니다. 호스팅된 회사 기록과는 별개이며, 그 구분은
[무엇이 어디 사는지](/ko/what-lives-where)에 있습니다. 호스트 백업에는 호스팅
서비스에 없는, 이 컴퓨터의 모든 것이 담깁니다.

## 백업과 복원

Linux에서는 명령 하나로 호스트 전체를 아카이브 하나에 쓰고, 다른 명령 하나로
되살립니다.

```bash
sudo internkim backup
sudo internkim restore /var/lib/internkim-backups/internkim-backup-20261001T031500Z.tar
```

백업하는 동안에도 서비스는 계속 돌아갑니다. 데이터베이스는 한 시점의 내용을 읽는
`pg_dump`로 덤프하고, 파일 가운데 SQLite 데이터베이스는 SQLite 자체 스냅숏으로
복사합니다. 아카이브에 담기는 것은 다음과 같습니다.

| | |
|---|---|
| 에이전트 데이터베이스 | 대화, 업무 이력, 원장, 기억과 그 임베딩 |
| 메신저 데이터베이스 | 모든 채널과 메시지 |
| `/var/lib/internkim` | 회사의 키, 사람마다 메시지에 서명하는 시드, 메신저 첨부 파일 |
| `/workspace` | 사람과 서클의 모든 파일, 소유자와 권한까지 |
| `/var/lib/internkim-relay` | 에이전트를 기다리는 메시지와 승인 질문 |
| `/root/.internkim` | 관리 게이트웨이의 데이터베이스와 설정 |
| `/etc/internkim` | 운영자 설정 |

호스트가 다시 만드는 것은 뺍니다. 메모리에만 있는 캐시,
`/workspace/shared/cache`의 의존성 캐시, 사람마다의 `tmp`, Python 런타임, 브라우저
프로필, 로그입니다.

### 매일 백업

패키지는 `internkim-backup.timer`로 하루에 한 번 `internkim backup --keep 7`을
실행합니다. 컴퓨터가 꺼져 있던 날의 백업은 다음에 켜질 때 합니다. 남길 개수를
바꾸려면 `/etc/internkim/company-host.env`에 `BACKUPS_KEPT`를 적으세요. 매일 백업을
끄려면 다음을 실행합니다.

```bash
sudo systemctl mask --now internkim-backup.timer
```

업그레이드해도 mask한 타이머는 꺼진 채로 남습니다. 다시 켜려면
`sudo systemctl unmask internkim-backup.timer`에 이어
`sudo systemctl enable --now internkim-backup.timer`를 실행합니다. 직접 만든
백업은 `--keep`을 주지 않으면 아무것도 지우지 않고, 정리할 때도
`internkim-backup-<시각>.tar` 이름의 아카이브만 지웁니다.

### 다른 곳에 사본 두기

지키려는 컴퓨터에 있는 아카이브는 그 컴퓨터와 함께 사라집니다. 또 암호화되어 있지
않습니다. 회사의 키와 사람들의 파일이 들어 있어서, 디렉터리와 아카이브는 root만 읽을
수 있습니다. 컴퓨터 밖으로 내보낼 때, 그 컴퓨터에 없는 키로 암호화하세요.
[age](https://age-encryption.org)와, 개인 키를 회사가 다른 곳에 보관하는 수신자로
암호화하는 예입니다.

```bash
sudo cat /var/lib/internkim-backups/internkim-backup-20261001T031500Z.tar \
  | age -r age1… > internkim-backup-20261001T031500Z.tar.age
```

암호화한 파일은 `rclone copy`나 `aws s3 cp`로 S3 호환 저장소에 올리면 됩니다. 키를
호스트에 두면 호스트를 가진 누구나 백업을 읽을 수 있고, 호스트를 잃으면 키도 함께
잃습니다.

### 다른 컴퓨터로 복원하기

새 컴퓨터에 설치하기의 첫 명령으로 패키지를 설치하고,
`internkim install`은 건너뛴 채 아카이브를 주어 `internkim restore`를 실행합니다.
새 컴퓨터가 호스팅 서비스에서 이전 컴퓨터의 자리를 이어받으므로, 이전 컴퓨터는 먼저
꺼 두세요.

복원은 무엇이든 바꾸기 전에 아카이브의 모든 부분을 기록된 체크섬과 대조합니다. 더
새로운 internkim이 만든 아카이브, 그리고 이 컴퓨터보다 새로운 PostgreSQL 메이저
버전에서 덤프한 아카이브는 거부합니다. PostgreSQL은 덤프를 같거나 더 새로운 메이저
버전으로만 복원하기 때문입니다. 그다음 서비스를 멈추고, 파일을 되돌리고, 아카이브에
든 명단으로 사람마다 계정을 다시 만들고, 모든 파일을 계정 이름으로 원래 소유자에게
돌려준 뒤, 두 데이터베이스를 복원하고 서비스를 시작합니다. 서비스는 시작하면서
스키마를 설치된 버전으로 올립니다. 설치처럼 복원도 에이전트가 명단을 받은 뒤에
끝납니다. 새 컴퓨터에 계정이 없는 소유자의 파일은 root
소유로 남고, 복원이 그 목록을 알려 줍니다.

백업을 만든 컴퓨터에 되살리려면 `--replace`를 붙이세요. 복원은 먼저 그 컴퓨터의
지금 상태를 백업하므로, 그 아카이브로 다시 `--replace` 복원하면 되돌릴 수 있습니다.

Mac에서는 데이터베이스가 Homebrew의 PostgreSQL이고, `internkim backup`과
`internkim restore`는 그것을 관리하지 않습니다. Mac에서는 두 명령이 거부합니다.

### 디바이스를 패키지로 옮기기

예전 디바이스 스택으로 돌던 디바이스는 `internkim recover -action migration-export`로
회사를 `/var/lib/internkim-migration/<시각>`에 내보냅니다. 디바이스 서비스를 멈추고
패키지를 설치한 뒤, 명령 하나가 그 디렉터리를 `/var/lib/internkim-backups`에
아카이브로 쓰고 복원합니다.

```bash
sudo internkim import-device /var/lib/internkim-migration/20261001T143757Z --connection internkim-host.json
```

디바이스는 연결 파일을 가진 적이 없으므로 연결 파일은 회사 설정에서 받습니다.
디바이스의 메신저 시드, 릴레이 키, 모델 키를 그대로 가져가므로 모든 사람의 메신저
키가 바뀌지 않습니다. 호스팅 서비스에 있는 디바이스 자신의 자격 증명은 그대로 둡니다.

### 아카이브 형식

바뀌지 않는 형식입니다. 이 형식으로 쓴 도구의 결과물은 백업처럼 복원됩니다.

아카이브는 압축하지 않은 tar이며, 다섯 멤버가 순서 없이 들어 있습니다.

| 멤버 | 내용 |
|---|---|
| `databases/blueclaw.dump` | 에이전트 데이터베이스의 `pg_dump --format custom`. 다른 역할이 소유한 객체는 복원할 때 `internkim`에게 넘어갑니다 |
| `databases/buzz.dump` | 메신저 데이터베이스의 같은 덤프. 커뮤니티가 하나뿐이면 호스트 릴레이 주소 `127.0.0.1:3000`으로 옮겨집니다 |
| `roster.json` | 에이전트가 쓰던 정책 문서. 사람과 서클이 계정이 됩니다 |
| `files.tar` | 파일. 항목 이름은 `<루트>/<경로>`이고 소유자와 그룹은 이름으로 기록합니다 |
| `manifest.json` | 아카이브가 무엇이고 무엇을 담았는지 |

매니페스트는 다음과 같습니다.

| 필드 | |
|---|---|
| `format` | `internkim-host-backup` |
| `formatVersion` | `1`. 복원은 자신이 읽는 것보다 새로운 버전을 거부합니다 |
| `createdAt` | 백업한 시각, RFC 3339 |
| `packageVersion` | 아카이브를 쓴 internkim 패키지. 버전 없는 빌드라면 비어 있습니다 |
| `companyID` | 이 호스트의 회사 |
| `postgresqlMajor` | 덤프를 뜬 PostgreSQL 메이저 버전 |
| `fileRoots` | `files.tar`에 든 루트 |
| `members` | 나머지 모든 멤버. 각각 `name`, 바이트 단위 `size`, 16진수 `sha256` |

매니페스트에 없는 멤버가 있거나, 크기나 체크섬이 다른 멤버가 있으면 아카이브 전체를
거부합니다. 데이터베이스 덤프는 없어도 되며, 그러면 그 데이터베이스는 빈 채로
시작합니다. `roster.json`도 없어도 되며, 그러면 계정이 없는 소유자의 파일은 root
소유로 남습니다. `files.tar`에는 `state` 루트가 있어야 하고, 그 안에
`companies/<companyID>/connection.json`과 `secrets` 디렉터리가 있어야 합니다. 항목은
디렉터리, 일반 파일, 심볼릭 링크, 하드 링크이며, 복원은 소유자를 번호가 아닌 이름으로
찾습니다. 루트는 다음과 같습니다.

| 루트 | 이 컴퓨터의 위치 |
|---|---|
| `state` | `/var/lib/internkim` |
| `relay` | `/var/lib/internkim-relay` |
| `configuration` | `/etc/internkim` |
| `administration` | `/root/.internkim` |
| `workspace` | `/workspace` |

압축은 `pg_dump`가 덤프에 하는 것뿐입니다. `files.tar`에 든 것은 대부분 사진과
문서처럼 이미 압축되어 있습니다.

## 답 크기

전송 한도를 넘는 답에는 릴레이가 바이트 수와 함께 `413`으로 응답합니다. 기본
상한은 3,000,000바이트이며 `ANSWER_BYTE_CEILING`으로 바꿀 수 있습니다. 0 이하의
값은 호스트 시작을 막습니다. 프로필 사진 한도는 base64 인코딩으로 크기가
늘어나는 만큼 이 상한에서 계산합니다.

## 네트워크 연결

호스트는 바깥으로 연결하고 로컬 인터페이스에서만 요청을 받습니다. 아직 회사가
없는 Linux 호스트만 예외로, 연결될 때까지 포트 18088에 연결 코드를 띄웁니다.
컴퓨터 관리는 같은 네트워크의 셸이나 회사가 관리하는 원격 접속 방법을 사용하세요.

Linux에서 패키지를 설치하거나 업그레이드할 때는 호스트가 쓰는 하나뿐인 Python
런타임을 `github.com`에서 받아 `/opt/internkim/python`에 두고, 첨부 문서를 읽는
고정된 라이브러리와, 번들 스킬마다 setup이 스킬 파일 옆에 두는 것을
내려받습니다. Python 라이브러리는 `pypi.org`와 `files.pythonhosted.org`에서, office 스킬의 페이지 렌더러는
`registry.npmjs.org`에서 받습니다. 하나라도 닿지 않으면 설치가 멈추고 무엇을 받지
못했는지 알려 줍니다. 배포판의 Python은 필요하지 않습니다. 스킬도 같은 런타임에서
각 사람 명령의 `python3`로 돌고, 누가 처음 쓸 때 아무것도 설치하지 않습니다.
