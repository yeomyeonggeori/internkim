Ask for a spreadsheet cleaned up, a deck built, a script run, and the work
happens in your workspace: a directory on the host that belongs to your own
Linux user. The tools here are built into the agent host (blueclaw), and every
one of them executes as you, so what the agent can touch is exactly what you
could touch at a shell.

## The tools [#tools]

| Tool | What it does |
|---|---|
| `read` | reads a workspace file or a conversation attachment: text as text, documents as converted Markdown, images as an image the model sees |
| `write` | creates or overwrites one text file |
| `edit` | applies exact text replacements as one atomic edit |
| `bash` | runs one command in the workspace |
| `file_delete` | removes one file, after you approve it |
| `file_deliver` | attaches finished files to the reply you receive |

`file_read` and `file_preview` read an exact line range or a document's
preview. The rest of the model's kernel, `plan`, `equip`, `ask_input`, and the
skill and memory tools, touches no file of yours.

Registered in `.dependency/blueclaw/internal/agentruntime/file_tools.go` and
`shell_tools.go`; the names live in
`.dependency/blueclaw/.dependency/blueprotocol/toolcontract/kernel_tools.go`.
The file tools are not a separate code path: each builds a shell command and
runs it through the same requester primitive as `bash`
(`internal/agentruntime/requester_shell.go`), starting in your own `$HOME`, so
tilde expansion, globs, and relative paths behave as they do at a shell.

## Who a command runs as [#identity]

Every person in the policy projects to a real Linux user and every circle to a
real group (`.dependency/blueclaw/internal/security/posix_identity.go`). A
person's circles are the ones the company places them in:

| Policy object | Linux object |
|---|---|
| person | `bc_person_<shortID>` user, with a primary group of the same name |
| circle | `bc_circle_<circleID>` group |
| everyone | `bc_shared` supplementary group |
| service internals | `blueclaw` user |

The daemon never touches a requester file itself. Workspace I/O and process
execution go through `blueclaw-posix-helper`, a setuid bridge that authorizes
only a real UID of `root` or `blueclaw`, then drops to the requester's UID,
GID, and supplementary groups before executing. After that drop the process
cannot regain privilege.

There is no allowlist of commands and no path filter anywhere. What the
guardrail (`internal/security/command_guardrail_service.go`) enforces is
structural:

- refuses to execute at all when the daemon is effectively root
- resolves the working directory against the workspace root
- replaces the environment with a fixed allowlist of variable names and a
  canonical `PATH`
- caps the timeout and output size
- requires bubblewrap when `terminal.mode` is `sandbox`

Ownership and mode bits make the access decision, which is why a
system-modifying command simply fails for an unprivileged actor. The
[boundaries](/boundaries) page has the design argument.

## The workspace layout [#layout]

| Path | Who may touch it | Holds |
|---|---|---|
| `private/people/<personID>` | you | your `$HOME`: durable personal files |
| `private/people/<personID>/tmp/<task>` | you | drafts and build intermediates |
| `private/people/<personID>/artifacts/<slug>` | you | finished personal output |
| `private/protected/<personID>` | the service writes, you read | your memory |
| `circles/<circleID>` | the service writes, the circle reads | that circle's memory |
| `shared/cache/dependencies` | everyone | package caches only |
| `skills` | read and execute | bundled skill source |
| `.blueclaw` | the service only | policy, logs, internal state |

## How finished work leaves [#delivery]

```
write        tmp/<slug>/…          draft and build inputs
bash         cwd=tmp/<slug>        build, render, verify
             artifacts/<slug>/…    the finished output moves here
file_deliver attachments           attached to the reply you receive
```

`tmp/` is ephemeral and `artifacts/` is durable; the artifact manifest
(`internal/agentruntime/artifact_manifest.go`) tracks what a task produced by
those paths. A direct message and a group conversation both work in the
requester's home. What someone else should read is filed in the
[data room](/data-room/agent).

## Skills [#skills]

A skill is a bundled instruction set the agent loads when a task matches it:
building a deck, filing paperwork, reading the company's mail. The runtime picks them
before the turn starts, by retrieving candidates for the request and letting
a router settle which ones apply, and the model receives only the selected
`SKILL.md` body; the scripts, references, and assets bundled next to it load
when the work needs them.
Skills live under `/workspace/skills`, their scripts run as the requester like
any other command, and each `SKILL.md` is budgeted (the repository gate is
15 KB and 300 lines) because an oversized skill is a prompt-runtime bug.

## When a human has to be there [#presence]

The agent does not sign in, pass MFA or solve a captcha for anyone. In its
browser it hands the page to you with `browser_handoff`
([approval](/tools#approval)); anywhere else it says what blocks it
and stops. A question the agent has to put to you goes through `ask_input`,
which parks the task until you answer and shows its `choices` as a numbered
list you can press. You may always answer in your own words.
