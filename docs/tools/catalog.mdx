The tables below are rendered at build time from the catalog the agent itself
reads (`pkg/capabilityprotocol/generated/capability-tools.json`, protocol
<ToolProtocolVersion />), so they cannot drift from what is deployed. The
descriptions are the exact English sentences the model receives.

The approval column marks the tools that pause for
[approval](/docs/tools/index#approval) before running. It is read from the
catalog's own `requiresApproval`, so no list here can fall behind it.

## Tasks [#task]

<ToolCatalog namespace="task" />

Answered on the central plane by
`web/src/lib/server/public-api/record/task-tools.ts`, against the record's own
`task` table, running as the calling member so row level security decides what
each call may see. Updates and deletes take a `taskHint`: the exact task ID or exact current title from a
`task_list` result. Dates are `yyyy-mm-dd`; the agent resolves "next Friday"
before calling.

`task_list` answers the current week when neither `weekFrom` nor `weekTo` is
given. Which week a task falls in follows its status rather than its dates
alone: planned or paused work that has not started yet rolls forward into the
week being read, so nothing planned is ever out of sight, and completed,
rejected or stopped work stays in the week it ended in. `query` matches the
title, business, type, owner's name and status, ignoring case and spacing.

Adding the same title for the same owner twice within ten minutes updates the
first task and answers with it. No second task is made.

## People [#person]

<ToolCatalog namespace="person" />

Answered on the central plane from the company's own member directory. It
answers who a person is and who works here. It is not a
step before a hint: a hint takes the fragment as it was written and the server
resolves it, and this is what the agent reads when a hint comes back with
candidates to choose between.

## Calendar [#calendar]

<ToolCatalog namespace="calendar" />

Answered on the central plane by
`web/src/lib/server/public-api/record/event-tools.ts`; a calendar event is a
task with a time span. Times are ISO
timestamps with a time zone, answered where the company is,
and `eventHint` follows the same resolution rule as `taskHint`.

`event_list` answers what is coming when no window is given: from the start of
today where the company is, through the seven days after it. Given one end of a
window and not the other, the missing end is a day away. `query` matches the
title, note and location, whatever the case.

`everyoneAttends` leaves the event with no attendee list, which is what open to
the whole company means; it does not name every member. An event whose
attendees do not include the person asking for it is being asked *of* them, and
stands at `requested` until they answer. Adding an event the company already
holds — same title, same time, same people — is refused with
`calendar_event_duplicate` and the id of the event it clashed with, so the
caller can update that one instead. There is no way to ask for it twice.

## Leave [#leave]

<ToolCatalog namespace="leave" />

Implemented on the central plane in
`web/src/lib/server/public-api/record/leave-tools.ts`, against the record's
own `leave` table and its `leave_in_full` and `member_leave_remaining`
functions, running as the calling member so row level security decides what
each call may see. The quantity is `days` as a number and the type is the
company's own registered kind; whether a leave is paid and whether it consumes
the entitlement follow from that kind, so the agent names the kind and the
record decides the rest. `leave_decide` is gated, because approving is what
spends the entitlement.

## Attendance [#attendance]

<ToolCatalog namespace="attendance" />

Implemented on the central plane in
`web/src/lib/server/public-api/record/attendance-tools.ts`, against the
record's `attendance` table and its `attendance_add`, `attendance_correct`,
and `attendance_remove` functions, running as the calling member. Days are
`yyyy-mm-dd`, times are 24-hour `HH:MM`, and both are read in the company's
time zone. `attendance_list` covers the last thirty days unless `from` and
`to` say otherwise. The authenticated web request carries the user's session
JWT; a personal `ik_` token is converted server-side to that member's JWT, so
the database call remains member-scoped and never writes with the service key.
For an ordinary self clock, omit `personHint`, `date`, and `time` from
`attendance_add`. One request writes the current moment and returns the existing
`result` fields `status`, `eventID`, and `backdated`, plus `result.event`
(`id`, `personID`, `kind`, `occurredAt`, and `location`). Historical and
administrator writes that save an event return the same `result.event`; the
`asked` response has no event. Use that recorded time and location in the UI;
there is no need to refresh with `attendance_list`. Notifications for this
live path start after the save in the background, so its response has no
`notified` field. Historical and administrator attendance writes retain their
existing `notified` response. A `reason` is optional and is kept when supplied.
A member writes, corrects, and removes their own records from the last three
days. Reaching further back, and touching anybody else's, is an administrator's:
asked by anybody else the call answers `asked`, the administrators are told what
was wanted, and nothing is written until one of them writes it.
A correction keeps what the record held before it, and a removal keeps who
removed it and why.

## CRM [#crm]

<ToolCatalog namespace="crm" />

Answered on the central plane by
`web/src/lib/server/public-api/record/crm-tools.ts`, against the record's
`organization`, `contact` and `opportunity` tables and its
`crm_opportunity_close` function, running as the calling member. An
organization, a person at one, and a deal are each named by a hint: an exact id,
or the name or current title a list result shows.

A deal stands at one of six stages: `waiting`, `in_progress`, `review`, `done`,
`on_hold`, `lost`. They are declared once as the record's `crm_stage` type,
which the catalog and the screens both read. `crm_opportunity_move` is the only
way a deal changes stage. A move into `done` or `lost` settles what the deal was
worth in the company's own currency, converting it when the deal is held in
another, and losing one needs a written reason. Naming a position and no stage
reorders the deal where it stands.

An activity is a task: `task_add`, `task_update` and `task_list` take
`organizationHint` and `opportunityHint`, so the work recorded against a deal is
the company's ordinary work. The screens and the API reach the same rows through
`crm_activity_save` and `crm_activity_list`, which are not offered to the model
and which write through the writers `task_add` and `event_add` already use.

## Messages [#message]

<ToolCatalog namespace="message" />

Implemented in `internal/capabilityd/platform_message_tool.go` and
`mattermost_tool.go`. `message_search` has two modes: keyword `queries`
return IDs with a preview around the match, and `messageIDs` returns those
messages complete. `message_update` edits one exact span of the agent's own
earlier message: `oldText` must occur exactly once, and the rest of the
message stays untouched. `message_send` targets a direct message, a named
channel, or the current conversation; only the current-conversation targets
skip approval.

## Channels [#channel]

<ToolCatalog namespace="channel" />

Implemented in `internal/capabilityd/mattermost_tool.go`. Display name,
header, and membership changes all go through this one gated tool.

## Web [#web]

<ToolCatalog namespace="web" />

Implemented in `internal/capabilityd/web_tool.go` through OpenRouter's web
search. Domain allowlists, language, and location narrow the query.

## Sites [#site]

<ToolCatalog namespace="site" />

Implemented in `internal/capabilityd/site_tool.go` over admind. The agent
builds a site as ordinary files in the workspace, then serves that directory:
`preview` returns a temporary review URL, `publish` takes the public one. The
slug is derived from the title on first serve and owned by the server.
`site_unserve` frees the slug and deletes the server-side record; the source
files in the workspace stay.

## Reading files and attachments [#document]

The model reads with one built-in tool, `read`: a workspace path or an
attachment's exact url from the conversation. Text comes back as text,
documents (HTML, PDF, DOCX, PPTX, XLSX, and friends) as converted Markdown,
images as an image the model sees — the runtime picks the modality from the
content type, so there is nothing to choose. The converters behind it are
implemented in `internal/capabilityd/file_read_tool.go` (with
`file_read_helper.py` doing format extraction) and are not exposed to the
model directly.

## Browser [#browser]

<ToolCatalog namespace="browser" />

Implemented in `internal/capabilityd/browser_tool.go`. Calls route to the
companion on the user's own computer when it is connected, with the device
browser as the other provider. `browser_open` requires the user present, and
responses carry no cookies, profile paths, or local screenshot paths;
`browser_screenshot` uploads to a temporary workspace-visible path instead.
Login, MFA, and captcha steps are handed to the human.

## Artifacts [#artifact]

<ToolCatalog namespace="artifact" />

Implemented in `internal/capabilityd/artifact_review_tool.go`. This is the
agent's own quality loop: it renders what it built, screenshots it, and asks
for typed visual issues against the stated intent before delivering.
