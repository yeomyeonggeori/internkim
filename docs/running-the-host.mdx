The company host runs on Debian 13, Ubuntu 22.04 or 24.04, Fedora,
RHEL-compatible 10 (Rocky, AlmaLinux) or Arch Linux, on arm64 or amd64, or on a
Mac with Apple silicon through Homebrew. The Linux packages
need glibc 2.35 or newer. The host needs an outbound internet connection and must stay awake. The
installer registers native services with systemd on Linux or launchd on macOS.
It needs no public address, inbound port, or Docker installation.

## Install

Download the connection file from the company setup page, then run:

```bash
curl -fsSL https://intern.kim/install.sh | sh -s -- host
sudo internkim install ~/Downloads/internkim-host.json
```

The first command installs the package through apt, dnf, pacman or Homebrew. On
Linux it fetches the package for this machine from our GitHub Releases and
checks it against the release's `SHA256SUMS` before the package manager installs
it. On a Mac it adds our Homebrew tap, `yeomyeonggeori/tap`, and installs the
`internkim` formula, whose bottle comes from the same GitHub Release and is
checked against the checksum the formula carries. The second command configures the company, asks for the OpenRouter API key,
and registers the host services. They start with the computer and recover after
a service exits. Installation finishes once every service answers and the agent
holds the company's roster, so a member can write to it right away. Then open the
printed company setup address and choose Check connection.

On Linux the connection file is optional. After the first command alone, the
computer waits for a company and shows an eight-character code at
`http://<computer>.local:18088/` on its own network; `sudo internkim box code`
prints the same code. An administrator on that network enters it on the company
setup page, checks the last four characters of the computer's key, and confirms.
The setup page then asks for the OpenRouter key. [Kim mini](/kim-mini)
describes how the claim works and how Disconnect undoes it.

## Upgrade

Run the first command again. On Linux it installs the release the channel now
points at over the version you have; on macOS Homebrew upgrades the formula. The
company and its data stay in place. The default channel is the latest release.
On Linux, to follow the newest release, prereleases included, add
`--channel testing`:

```bash
curl -fsSL https://intern.kim/install.sh | sh -s -- host --channel testing
```

The tap carries only the latest release, so a Mac stays on the default channel.

On a connected Linux host the upgrade rewrites the settings the first install
wrote, prepares the database again, restarts the services and returns once every
one of them answers and the agent holds the roster again. If one does not, it
names that service and how to read why; `sudo internkim refresh` runs the same
steps again once that is fixed. A message that arrives while the agent restarts
waits in the messenger's queue and is answered when the agent is back.

## Remove

```bash
sudo apt remove internkim     # Debian, Ubuntu
sudo dnf remove internkim     # Fedora, RHEL-compatible
sudo pacman -R internkim      # Arch Linux
```

Removing the package stops and disables the host services and deletes the
program files, the host's Python runtime and what it prepared for the skills.
The install added no package source or signing key. The company stays on the
computer: `/var/lib/internkim` holds its key on the hosted service and the seed
that signs messages as each person, and `/var/lib/internkim-postgres` and
`/var/lib/internkim-cache` hold the host's database and cache. Installing the
package again brings the same company back. On Debian and Ubuntu,
`sudo apt purge internkim` also deletes the settings in `/etc/internkim`.

Neither key can be issued again, so deleting the company is left to you. The
last directory holds its backups:

```bash
sudo rm -rf /var/lib/internkim /var/lib/internkim-postgres /var/lib/internkim-cache /var/lib/internkim-backups
```

## Check services

On Linux, systemd shows the host service state and logs:

```bash
systemctl list-units 'internkim*' 'blueclaw*' 'buzz*'
systemctl status internkim-relay
journalctl -u internkim-relay -n 50 --no-pager
```

On macOS, run `launchctl print system/kim.intern.<service>` to inspect a
service. Its logs are under `/var/log/internkim/`.

## Settings

The installer writes company connection details and generated credentials to
the protected host data directory. Most companies do not need to edit these
files. Optional operator settings go in
`/etc/internkim/company-host.env`. The generated [host settings
reference](https://github.com/yeomyeonggeori/internkim/blob/main/host/README.md)
lists the supported variables and their defaults. Keep API keys and connection
files out of the settings file.

## Local data

The computer holds the agent's conversation history, task history, memory,
workspace files, and messages waiting for delivery. These are separate from
company records in the hosted service, which [What lives where](/what-lives-where)
describes. A backup of the host holds everything on this computer that the hosted
service does not.

## Back up and restore

On Linux, one command writes the whole host to one archive and another brings it
back:

```bash
sudo internkim backup
sudo internkim restore /var/lib/internkim-backups/internkim-backup-20261001T031500Z.tar
```

The services keep running while a backup is taken. Each database is dumped with
`pg_dump`, which reads it as of one moment, and every SQLite database among the
files is copied through SQLite's own snapshot. The archive holds:

| | |
|---|---|
| The agent's database | conversations, task history, the ledger, memory and its embeddings |
| The messenger's database | every channel and message |
| `/var/lib/internkim` | the company's keys, the seed that signs messages as each person, the messenger's attachments |
| `/workspace` | every person's and circle's files, with their owners and modes |
| `/var/lib/internkim-relay` | messages and approval questions still waiting for the agent |
| `/root/.internkim` | the admin gateway's own databases and settings |
| `/etc/internkim` | the operator's settings |

It leaves out what the host rebuilds: the cache, which lives in memory, the
dependency caches under `/workspace/shared/cache`, each person's `tmp`, the
Python runtime, the browser's profiles and the logs.

### The daily backup

The package runs `internkim backup --keep 7` once a day through
`internkim-backup.timer`. A day the computer was off is caught up when it next
starts. To keep another number of backups, set `BACKUPS_KEPT` in
`/etc/internkim/company-host.env`. To turn the daily backup off:

```bash
sudo systemctl mask --now internkim-backup.timer
```

An upgrade leaves a masked timer off. `sudo systemctl unmask internkim-backup.timer`
and then `sudo systemctl enable --now internkim-backup.timer` turn it back on.
A backup made by hand prunes nothing unless it is given `--keep`, and pruning only
ever removes archives named `internkim-backup-<time>.tar`.

### Keep a copy elsewhere

An archive on the computer it protects does not survive that computer. It is
also unencrypted: it holds the company's keys and its people's files, and the
directory and every archive in it are readable by root alone. Encrypt it as it
leaves the computer, to a key that does not live there. With
[age](https://age-encryption.org) and a recipient whose private key the company
keeps elsewhere:

```bash
sudo cat /var/lib/internkim-backups/internkim-backup-20261001T031500Z.tar \
  | age -r age1… > internkim-backup-20261001T031500Z.tar.age
```

The encrypted file can then go to any S3-compatible store with `rclone copy` or
`aws s3 cp`. A key kept on the host would make the backup readable by anyone who
had the host, and lost with it.

### Restore onto another computer

Install the package on the new computer with the first command under
Install, skip `internkim install`, and run `internkim restore` with
the archive. The new computer takes over the old one's place on the hosted
service, so turn the old one off first.

The restore checks every part of the archive against its recorded checksum before
it changes anything. It refuses an archive made by a newer internkim, and one whose
databases came from a newer PostgreSQL major than this computer runs, because
PostgreSQL restores a dump into the same or a newer major only. It then stops the
services, puts the files back, recreates each person's account from the roster in
the archive, gives every file back to its owner by account name, restores both
databases and starts the services, which bring their schemas up to the installed
version. Like the install, it returns once the agent holds the roster. A file whose owner has no account on the new computer stays owned by root,
and the restore lists it.

To restore onto the computer the backup came from, add `--replace`. The restore
first backs up what the computer holds now, so `--replace` with that archive undoes
it.

On a Mac the database is Homebrew's PostgreSQL, which `internkim backup` and
`internkim restore` do not manage. They refuse there.

### Move a device onto the package

A device running the older device stack writes its company with
`internkim recover -action migration-export`, into
`/var/lib/internkim-migration/<time>`. With the device's services stopped and the
package installed, one command writes that directory as an archive in
`/var/lib/internkim-backups` and restores it:

```bash
sudo internkim import-device /var/lib/internkim-migration/20261001T143757Z --connection internkim-host.json
```

The connection file comes from company setup, because a device never held one.
The device's messenger seed, relay key and model key are carried, so every
person's messenger key stays the same. The device's own credentials on the hosted
service are left as they were.

### The archive format

This is a stable format. A tool that writes it is restored like a backup.

The archive is an uncompressed tar of five members, in any order:

| Member | Contents |
|---|---|
| `databases/blueclaw.dump` | `pg_dump --format custom` of the agent's database. A restore gives objects owned by any other role to `internkim` |
| `databases/buzz.dump` | the same, of the messenger's database. When it holds one community, that community is moved to the host's relay address, `127.0.0.1:3000` |
| `roster.json` | the policy document the agent was running, whose people and circles become accounts |
| `files.tar` | the files, each entry named `<root>/<path>` with its owner and group recorded by name |
| `manifest.json` | what the archive is and what it holds |

The manifest:

| Field | |
|---|---|
| `format` | `internkim-host-backup` |
| `formatVersion` | `1`. A restore refuses a version newer than it reads |
| `createdAt` | when the backup was taken, RFC 3339 |
| `packageVersion` | the internkim package that wrote it, empty for a build without one |
| `companyID` | the company whose host this is |
| `postgresqlMajor` | the PostgreSQL major the dumps were taken from |
| `fileRoots` | the roots `files.tar` holds |
| `members` | every other member, each with `name`, `size` in bytes and `sha256` in hex |

A member the manifest does not list, or one whose size or checksum differs, makes
the whole archive refused. A database dump may be absent, and that database then
starts empty. `roster.json` may be absent, and a file whose owner has no account
then stays owned by root. `files.tar` must hold the `state` root, with
`companies/<companyID>/connection.json` and its `secrets` directory. Its entries
are directories, regular files, symbolic links and hard links, and a restore
resolves owners by name and never by number. The roots:

| Root | On this computer |
|---|---|
| `state` | `/var/lib/internkim` |
| `relay` | `/var/lib/internkim-relay` |
| `configuration` | `/etc/internkim` |
| `administration` | `/root/.internkim` |
| `workspace` | `/workspace` |

The dumps are compressed by `pg_dump` and nothing else is. Most of what
`files.tar` holds, pictures and documents, is compressed already.

## Answer size

The relay replies with `413` and the byte count when an answer exceeds its
transport limit. The default ceiling is 3,000,000 bytes; set
`ANSWER_BYTE_CEILING` to change it. A non-positive value prevents startup.
Profile-picture limits are derived from this ceiling because base64 encoding
increases their size.

## Network access

The host opens outbound connections and listens only on local interfaces. The
exception is a Linux host that belongs to no company yet, which serves its
pairing code on port 18088 until it is claimed. To administer the computer, use
a shell on the same network or a remote access method your company controls.

On Linux, installing or upgrading the package also downloads the host's one
Python runtime from `github.com` into `/opt/internkim/python`, the pinned
libraries that read attached documents, and what each bundled skill's setup
keeps beside the skill's files: Python libraries from `pypi.org` and
`files.pythonhosted.org`, and the office skill's page renderer from
`registry.npmjs.org`. If any of them is unreachable, the install stops and names what it could not fetch. The host needs no Python
from the distribution. The skills run on the same runtime, as `python3` in each
person's commands, and install nothing the first time someone uses them.
