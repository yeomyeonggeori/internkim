A member turns notifications on for one device, and the plane pushes to it.
There is no notification inbox. The thing a notification is about stays where
it always was, so a missed push costs only the interruption. The Buzz relay
keeps how far each member has read every conversation and thread, and counts
what is unread from there, so their other devices agree on it. The
conversation list shows that count; when the relay can only say "at least", the
badge carries a plus, and when it cannot say, there is no badge. The
messenger's inbox holds the messages that call on the member and the latest
reply of each thread with replies they have not read.

## What sends what [#categories]

| Category | Sent when | Reaches |
|---|---|---|
| `message` | the relay sees a message addressed to someone | those addressed |
| `attendance` | a member clocks in or out | everyone else in the company, or as far as each listener narrowed it |
| `leave` | a member asks for leave | the administrators, minus the asker |
| `task` | a task moves between statuses, or someone is added to one | for a move, the requester and the participants; for an addition, whoever was added. Never whoever wrote it |
| `calendar` | an event's reminder lead time is reached | the members on that event |
| `approval` | an agent run needs a person | the requester |
| `mail` | new mail arrives | the account's owner |

`attendance`, `leave`, `task` and `calendar` come from the central plane and
need nothing else running. `message`, `approval` and `mail` come from the
company's computer: its relay reads the messages, and the agent's runs
and the mailbox are things only it can see. Every category is on by default
except `mail`.

A message notification carries the message as plain text, cut at 140
characters with an ellipsis. Markdown marks are dropped, a list item keeps its
bullet or number, a table becomes one line per row and a link keeps its text.
An attachment is named in the reader's language, `[Photo]`, `[Video]` or
`[File]` in English and `[사진]`, `[동영상]` or `[파일]` in Korean. The
message's first picture, when it is a JPEG, PNG or GIF of at most 5 MiB, travels
with the notification as its image.

Two switches decide whether a push is sent, and both belong to the person: the
category switch in their settings, and whether they muted that conversation.
Both live in the member's `preferences`, as `notificationSettings` and
`mutedChannels`. The company's computer sets one mute on the person's behalf.
Creating a channel, in the web app or through the agent, makes every company
administrator an owner of it, and an administrator nobody invited starts that channel muted and can
unmute it like any other conversation. Attendance also has a reach,
`attendanceReach` in the same settings: `everyone`, `teamAndSupervisors` (My
team and supervisors) for the member's own team and every supervisor above them
up to the top, or `team` (My team) for their own team alone. A supervisor in another team still counts. A member with
no device subscribed is never reached at all, which is the state everyone
starts in.

## The key pair [#keys]

Web push is signed, so the plane holds a VAPID pair in its vault. Replacing
the pair silently unsubscribes every device that holds the old one, so it is
set once. Founding a company sets it: `POST /api/company` calls the
`setup-vapid` edge function with the founder's token and reports the outcome as
`notifications`. An administrator can make the same call by hand for a
deployment founded before that existed.

`setup-vapid` never replaces a standing pair and answers `{"stored":false}`
when one is kept. When the vault holds no pair but web-push devices are
already subscribed, it refuses with `409`, since a fresh pair would sign every
send with a key no device accepts. A deployment in that state adopts the pair its
devices already carry with `public.vapid_keys_keep`, called with the service
key. The edge functions that send answer `503` while any of the three values
is missing.

## Reminders run on a schedule [#reminders]

Every other notification is sent by the request that caused it. A calendar
reminder has no such request, so `pg_cron` runs
`announce_event_reminders()` every minute and posts the events that are due to
the `announce-event-reminder` edge function. An event with no lead time
reminds nobody. The hourly question about shifts nobody closed runs the same
way.

Both read an address and a secret from the vault. The migration that creates
the jobs also creates their secret, `scheduled_job_secret`, and the receiving
side checks it with `is_a_scheduled_job()`, which only the service role may
call. The secret belongs to the plane and to no company. The addresses are
stored by the founding call. With no address stored, the schedule sends
nothing and raises nothing, so a self-hosted install that is not set up yet
stays quiet.

The secret opens those two jobs and nothing else, and it never leaves the
database except in their requests, so it is not rotated on a schedule. If it
may have leaked, replace it in the SQL editor:

```sql
select vault.update_secret(
  (select id from vault.secrets where name = 'scheduled_job_secret'),
  encode(extensions.gen_random_bytes(32), 'hex')
);
```

Both sides read the vault on every call, so the next call carries the new
value and nothing needs redeploying. A request already queued when it changes
arrives with the old one and is refused, which can drop that minute's
reminders. Run it just after the minute turns.

## What the platforms do differently [#platforms]

| | Safari, any Apple device | Android Chrome | Desktop Chrome |
|---|---|---|---|
| Needs installing first | on iOS, to the home screen | no | no |
| Custom notification icon | ignored, the app icon is used | shown | shown |
| Its own entry in system settings | yes | when installed as a WebAPK | no, it is Chrome's |
| What the notification is labelled | the installed name | the installed name | Chrome, then the origin |

WebKit drops the icon a notification carries, so the sender's name leads the
body text. An Android phone that shows notifications only when the app is
opened has put Chrome to sleep: the push arrived and waited, and battery
optimisation for Chrome is what holds it.

The internkim app receives the same pushes through APNs on Apple devices and
FCM on Android, and draws them itself. On the first sign-in on a device it asks once
for notification permission, then, in the desktop app, whether internkim may
use the computer. A person who declines turns notifications on later in
Settings → Notifications.

| | iPhone | Android | Mac |
|---|---|---|---|
| Sender's picture | shown | shown | shown |
| The message's picture | not drawn | expanded below the text, the sender's picture as its icon | not drawn |
| A push while the app is open | a banner, except for the conversation on screen | posted like any other | a banner, except for the conversation on screen, which leaves nothing in Notification Center either |

The attendance widget on an iPhone follows a clock-in or clock-out made
elsewhere through a silent push that wakes the app. iOS holds those pushes back
when Background App Refresh is off for the app or for the whole phone, and in
Low Power Mode. The widget then changes only when the app is opened or the
widget is pressed. The app says so once above the tab bar, with a button to its
Settings page, and says it again if the setting is turned on and later off.
